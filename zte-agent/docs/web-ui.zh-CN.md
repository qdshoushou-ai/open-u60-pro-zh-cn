# 已归档的服务端渲染 UI

本文描述的是已退役的界面。生产环境不再提供它。`/` 和 `/ui/` 现在打开响应式控制台；参见[当前指南](responsive-console.md)。共享的证书/安全辅助代码和渲染器回归测试夹具仍在内部保留。

# Web UI：`/ui/`

Agent 在与 JSON API 相同的监听器上提供浏览器 UI（端口 9090）；当所有者开启后，还会用路由器自己的证书颁发机构在 9443 端口上提供 HTTPS（[局域网 HTTPS](#局域网-https)）。它是 iOS App 的逐标签页复制（仪表盘、短信、工具、路由、设置），界面、措辞和流程都相同：仪表盘及其 USB-C 卡片和多个面板（连接与信号、实时流量、电池详情、CPU 与温度、CPU 与内存、进程、Wi-Fi 与设备及共享 Wi-Fi）、网络模式、工具列表及其自动化（新建/编辑自动化）、网速测试、启用 ADB、USB 模式、频段锁定、AT 终端、设备信息、已连接设备、App 对其外壳工具的占位页，以及仍留在 App 中的两个工具的说明（局域网测速、配置解密/加密）、路由 › 移动网络（移动数据、飞行模式、连接模式、数据漫游、网络选择及其扫描和手动注册，以及 App 的“需要重启”）、小区锁定（含邻区扫描）、智能基站连接（Smart Tower Connect）、信号检测、SIM 卡（含 PIN、PUK 和解锁码面板）、eSIM 配置文件（切换、重命名、删除、运营商回执、芯片卡，以及从二维码照片或激活码添加 eSIM）、SIM 服务（USSD 和 SIM 工具箱）、WiFi、访客 WiFi、APN（含新建/编辑 APN 和自动 APN）、局域网/DHCP、DNS（含 DoH 缓存检查器）、防火墙（含新建端口转发）、遥测拦截、VPN 透传、QoS 和设备控制（充电上限、节能模式、快速启动、带空闲超时的自动休眠、重启路由器和用路由器密码执行的恢复出厂设置）、短信 › 消息及其会话（打开、回复、删除）和新建消息、短信转发（其开关、规则、带“测试目标”的新建/编辑规则、带重试和清除的转发日志；也在工具下），以及设置（会话及退出登录、轮询刷新间隔、外观主题、HTTPS 与安装为 App 及安装到你的设备、关于、法律声明）。Web 版省略的内容列在[未提供的 Web 功能](#未提供的-web-功能)下。用户请见 README 的 [Web UI](../../README.md#web-ui) 一节；本页面向贡献者。

- 服务端渲染 HTML（[maud](https://maud.lambda.xyz/)）：每个插值都会被转义，`src/web` 下没有任何地方使用原始 HTML（有测试检查）。
- 页面在进程内调用 Agent 自己的处理函数和服务函数，绝不通过 HTTP 调用 Agent。
- 所有功能在不启用 JavaScript 时都能工作。[Datastar](https://data-star.dev/) 1.0.4 已内置并由 Agent 提供，是可选的实时层。
- 会话只存在于内存中：Agent 重启会让所有浏览器退出登录。
- 页面和动作都是表（`src/web/screen.rs`、`action.rs`，以及 `src/web/tabs/` 中的各标签页），由共享原语（`kit.rs`）绘制；一张路由表（`routes.rs`）为它们全部提供服务。

## 导航

- 每个已登录页面都有导航栏（标题居中；左侧是“‹ <父页面>”、仪表盘的状态胶囊或连接与信号的时长标记；右侧是“完成”或仪表盘的时长标记；两侧保持相同宽度，至少 4.5rem，因此标题始终居中，过长的返回标签或标题以“…”结尾）和五标签栏：手机上为底部浮动栏，宽屏上位于导航栏下方。两者都是普通链接，不涉及 JavaScript。
- App 中的面板在这里是页面，右侧为“完成”（连接与信号、实时流量、电池详情、CPU 与温度、Wi-Fi 与设备）；进程是叠在 CPU 与内存之上的面板，左侧为“完成”、右侧为“终止全部预装软件”，与 App 一致。被压入的页面带“‹ <父页面>”（路由 › 移动网络、所有工具页面；CPU 与内存，叠在 CPU 与温度之上的面板；共享 Wi-Fi，App 在其面板中展开的卡片）。警告是确认页面：导航栏中为“‹ <表单所在的页面>”和“确认”，页面标题（会换行）是问题本身，随后是会发生什么、按钮和取消。
- App 的 USB 模式面板会在插入 USB-C 线缆时自动覆盖在任何标签页上打开；Web 版把它做成仪表盘横幅之后的卡片（页面无法弹出面板，其他页面也不会为此采样）。
- 同一屏幕可以出现在两个标签页中：网络模式从连接与信号压入（`/ui/signal/network-mode`，仪表盘标签页），同时列在路由下（`/ui/router/network-mode`）；短信转发从消息的齿轮压入（`/ui/sms/forward`，“‹ 消息”），同时列在工具 › 自动化下（`/ui/tools/sms-forward`，“‹ 工具”）。每个挂载点都有自己的标签页、返回路径和表单目标。
- 消息页以齿轮（短信转发）开头、以新建消息结尾，与 App 一致；App 的呼叫按钮被省略（通话仅在 App 中提供；页面会说明这一点）。会话从消息压入（“‹ 消息”，保留存储过滤条件）。新建消息（App 的面板）左侧为“取消”。App 的滑动删除在这里是每行末尾的小“删除”链接，点击后打开确认页面。搜索期间，“搜索”旁的“取消”返回完整列表（对应 App 的搜索栏）。
- 新建规则/编辑规则（App 的面板）左侧为“取消”，返回短信转发；短信转发中每条规则行都有开关和“删除”链接（对应 App 的滑动），删除前会先询问。
- 转发日志从短信转发压入（“‹ 短信转发”，位于该挂载点的标签页）右侧为“清除”（对应 App 的工具栏按钮），清除前会先询问；失败条目的“重试”（对应 App 的滑动）是行末的小按钮。
- 工具按 App 的分区和顺序列出各行（`ToolsListView`），每行带 Android App 的副标题（iOS 的行没有副标题）；每行打开对应页面或说明。TTL 设置、启用 SSH 和设备浏览器打开 App 的占位页（其图标、标题和文字）；局域网测速和配置解密/加密打开同风格的说明：“局域网测速在 OpenU60 App 中。”（它在客户端测量，需要脚本）和“配置解密/加密在 OpenU60 App 中。”（App 标题为“配置工具”；它在手机上解密含凭据的配置文件）。进程仍放在仪表盘下（App 的位置；Android 也把它列在工具下）。
- 新建自动化/编辑自动化（App 的面板）左侧为“取消”，返回自动化；每条自动化行都有开关和“删除”链接（对应 App 的滑动），删除前会先询问。
- 网速测试、启用 ADB、频段锁定和 AT 终端从工具压入（“‹ 工具”）；它们的问题（Web 版的问题，以及 AT 终端的“危险命令”，即 App 的警告）是确认页面，确认后回到该工具。
- 路由的页面从路由压入（“‹ 路由”）：移动网络、网络模式、小区锁定、智能基站连接、信号检测、SIM 卡、eSIM 配置文件、SIM 服务、WiFi 设置、访客 WiFi、APN 设置、局域网/DHCP、DNS 设置、防火墙、遥测拦截、VPN 透传、QoS、设备控制。设备控制的密码面板——重启路由器和恢复出厂设置——是左侧为“取消”的页面；确认后进入“正在重启……”（或“正在重置……”）页面，除标签栏和“重新加载”外无路可退。对远程浏览器，开启自动休眠前会先在确认页面（“‹ 设备控制”）询问。防火墙的面板“新建端口转发”是一个页面（左侧为“取消”）；App 中滑动删除端口转发或被阻止的域名，在这里是行末的垃圾桶按钮，删除前会先询问。防火墙的各项问题（每个开关、级别、应用 DMZ、添加规则、删除规则）以及移除被阻止的域名都是确认页面（“‹ 防火墙”、“‹ 遥测拦截”）。APN 设置的面板是页面：新建 APN 和编辑 APN（左侧为“取消”；手动配置的行会打开编辑 APN，其“•••”菜单包含 App 的滑动操作、激活和删除）以及自动 APN（“完成”）。DNS 设置的“检查缓存”打开 DNS 缓存（“完成”）。WiFi、访客 WiFi、APN（模式、添加/保存、激活、删除）、局域网/DHCP 和 DNS（应用、清除缓存）的问题都是确认页面（“‹ <页面>”；取消会回到已填写内容的表单）；WiFi 应用后是“重新连接到……”，局域网应用后是显示新地址的页面。SIM 卡的面板（输入 PIN、启用 PIN 锁、停用 PIN 锁、更改 PIN、输入 PUK、SIM 解锁）是左侧为“取消”的页面，返回 SIM 卡；每个也都是独立的问题（见下文）。“需要重启”（App 在关闭飞行模式失败两次后的警告）从移动网络压入（“‹ 移动网络”）。应用（漫游）、注册、小区锁定与解锁以及 STC 控件的问题都是确认页面，确认后回到对应页面；扫描、注册以及连接模式或漫游的变更会在操作页面继续。
- eSIM 配置文件的右侧是 App 的工具栏：“+”（添加 eSIM）和刷新。它的对话框是从它压入的页面（“‹ eSIM 配置文件”）：“切换到……？”和“永久删除……？”（确认页面），以及重命名配置文件（App 的面板，左侧为“取消”）。App 的滑动和上下文菜单在这里是每个配置文件上的“•••”菜单（一个 `<details>`：重命名、删除配置文件）；点击可切换的配置文件会打开其问题，与 App 的点击一致。切换在操作页面继续（“‹ eSIM 配置文件”）。添加 eSIM（“+”、列表中的添加 eSIM、App 的面板）右侧为“完成”（下载运行时为“关闭”；因为它是实时的，下载结束后会显示“完成”），返回 eSIM 配置文件；其下载卡片即面板的进度视图，“立即切换”会进入 eSIM 配置文件的切换问题。
- 设置按 App 的顺序是一个标签页根：“会话”（“已在此浏览器登录”、“退出登录”；它取代 App 的网关和密钥链部分，这两部分没有对应的 Web 版本）、“轮询”、“外观”、“关于”、“法律声明”。轮询和外观的页脚是 App 的页脚加上“已保存在此浏览器中。”（它们是本浏览器的 Cookie）。外观之后是 Web 新增项：“HTTPS 与安装为 App”（[局域网 HTTPS](#局域网-https)）；其“安装到你的设备”从设置压入（“‹ 设置”），其开启、续期和重置问题都是确认页面（“‹ 设置”）。
- 登录页是 App 的页头（“ZTE U60 Pro”、“Router Companion”；上面没有“U60 Pro”品牌，因为 App 的登录页没有标题），加上 Web 版的“Agent 密码”和“登录”；其他未登录页面保留品牌。

## 未提供的 Web 功能

App 有而 Web UI 省略或替代的内容（所有者决策 21、28、40、42）：

## 请求处理流程

任何请求之前，监听器都会检查连接来源（`httpd::mobile`，所有者决策 53；API 同样如此）：来自移动数据侧的客户端会被直接关闭、不作回复，无论路由器的防火墙设置如何。允许服务的来源：回环地址（所有 Tailscale 客户端）、路由器自身的地址、从本地接口进来的 IPv6 链路本地地址，以及不属于 `rmnet*` 的接口（Wi-Fi 的 `br-lan`、USB 网络）子网内的地址——且该子网必须是包含该地址的最具体子网（内核会经它回复；若与某个 `rmnet*` 子网并列则不服务）。判断依据是客户端的地址，而不是它访问的地址，因此转发到路由器 LAN 地址的端口转发或 DMZ 也会被拒绝。接口表来自 `getifaddrs`，在阻塞池中读取（accept 循环最多等待 0.5 s，之后先用上一张表判断，读取在后台完成且不再启动其他读取；已建立的连接继续服务），触发时机是需要它的 accept（非回环）：表龄达到 5 s，或某连接将被拒绝时（后者每秒最多一次）。读取失败时保留上一张表 10 分钟；若连这样新的表都没有，则一律提供服务（只记录一次；此后 `mobile::mobile_served` 会把防火墙提问切换为旧措辞）；`ZTE_AGENT_ALLOW_MOBILE=1` 关闭该检查（其他值会被忽略并记录）。拒绝会记录一次，之后每分钟最多一行；不属于任何本地子网的客户端（端口转发或 DMZ 的客户端）记录为 "no local subnet, reached via <interface>"。

一个中间件（`src/web/mod.rs` 中的 `guard`）会在每个 `/`、`/ui` 和 `/ui/**` 请求上最先运行：

1. **Host 允许列表**（DNS 重绑定防护）：IP 字面量、`ZTE_AGENT_UI_HOSTS` 中的名称、局域网 HTTPS 名称（`u60.home.arpa`，仅经 HTTPS 监听器；该监听器只在 HTTPS 开启时运行：其他网络的 DNS 也可能为 `home.arpa` 名称作答，因此在 http 上它会成为重绑定目标，但其他人无法为该名称出示路由器的证书），以及仅来自回环对端（Tailscale 客户端）的 `localhost` 和路由器的 Tailscale 名称。否则 `403 Host not allowed`；没有 `Host` 则为 `400 Missing Host`。API 应用相同规则。
2. 每个 HTML 响应使用新的 CSP nonce。
3. 未设置 Agent 密码时，所有页面都是“设置 Agent 密码”页面（`403`）；资产和清单仍可加载。
4. 每个响应都带安全响应头：
   - `X-Frame-Options: DENY`、`Referrer-Policy: same-origin`、`X-Content-Type-Options: nosniff`、`Cross-Origin-Resource-Policy: same-origin`；
   - HTML：`Content-Security-Policy: default-src 'none'; script-src 'nonce-…'; style-src 'self'; img-src 'self'; connect-src 'self'; form-action 'self'; base-uri 'none'; frame-ancestors 'none'; manifest-src 'self'` 和 `Cross-Origin-Opener-Policy: same-origin`；
   - HTML 和实时流：`Cache-Control: no-store`。
5. 主题为浅色或深色的浏览器（设置 › 外观，`zte_ui_theme` Cookie：`light` 或 `dark`，其他值表示跟随系统）会让所有 HTML 页面（无论是否登录）都以该配色呈现（`prefs::themed`）：外壳原本按系统配色绘制的配色标签（`color-scheme: light dark` 和每种配色各自的导航栏颜色）会被替换为该主题的（`color-scheme` 和单一导航栏颜色），并在 `app.css` 之后追加 `theme-light.css` 或 `theme-dark.css`。不涉及 JavaScript；跟随系统主题的页面原样输出。

接着是会话、CSRF 和闸门：读取设备的页面工作像 API 调用一样等待通用通道许可；7 s 内没有可用许可时，页面返回 `503`“Router busy”并带重试链接。

## 会话与 CSRF

- Cookie：`zte_ui_session=<64 hex>; Path=/ui/; Max-Age=604800; HttpOnly; SameSite=Strict`（仅限主机；在 :9090 的明文 HTTP 上不带 `Secure`，在 :9443 的 HTTPS 上为 `__Host-zte_ui_session; Path=/; …; Secure`）。与之配合的标记为 `zte_ui_signed_in=1; …; SameSite=Lax`（不含机密；即前面提到的标记跳转）。清除时使用 `zte_ui_session=; Path=/ui/; Max-Age=0; HttpOnly; SameSite=Strict`。
- 会话在 12 h 未使用后失效，最长 7 天。最多保留 16 个；新登录会丢弃最近最少使用的会话。登录会替换浏览器出示的会话；退出登录会结束该会话及其实时流。
- `/api` 下从不读取 Cookie，`/ui` 下忽略持有者令牌。持有者令牌绝不会被当作 Cookie 接受，反之亦然。
- 每个请求最多尝试 16 个格式正确的会话 Cookie，因此同一主机上其他页面用更深路径植入的 Cookie（Cookie 不按端口隔离）无法把真正的那个挤出去。在 `ZTE_AGENT_UI_HOSTS` 中配置专用主机名，可把 Agent 的 Cookie 与 80 端口上原厂 Web UI 的 Cookie 区分开。
- **登录表单：** 一个 `zte_ui_pre` Cookie（`Max-Age=900`）加一个有效期为 15 分钟的 HMAC 表单令牌（其时间字段按进程偏移，因此不会泄露路由器的运行时间），以及供密码管理器使用的隐藏用户名字段。错误密码会像 API 一样计入同一限流（`429` 页面并带 `Retry-After`）。
- **`next`**（登录后返回的地址）：以 `/ui/` 开头，最多 200 字节，仅使用普通字符集，不含 `//` 或 `\`，不含点段（也包括 `%2e`），且绝不指向登录、退出、实时、资产或操作路径。否则回到仪表盘。
- **每个表单**（登录、退出、每一次变更）都带 CSRF 令牌：每个会话一个随机 32 字节机密，以常量时间比较。POST 还必须同源：`Origin` 必须与 `Host` 完全匹配（协议、主机、端口），没有 `Origin` 时则校验 `Referer`；`Sec-Fetch-Site` 不是 `same-origin`/`none` 时拒绝。任何失败都返回 `403` 页面且不做任何更改。
- 没有会话的 POST 绝不执行：登录页会显示“你的会话已过期。未做任何更改。”并引导回表单所在的页面。
- **经 HTTPS 时**（`httpd::tls`），上述每个 Cookie 都会变成带 `Path=/` 和 `Secure` 的 `__Host-` Cookie（`__Host-zte_ui_session`、`__Host-zte_ui_pre`、`__Host-zte_ui_theme`、`__Host-zte_ui_refresh`），因此同一主机的 http 与 https 源（Cookie 按主机而非端口划分）永不共享会话或偏好：TLS 边界只把本源的 `__Host-zte_ui_*` Cookie 交给应用（去掉前缀；浏览器一并发送的 http 侧 Cookie 会被丢弃），并把应用的 `Set-Cookie` 变成 `__Host-…; Path=/; Secure`（清除用的也如此）。`https://` 的 `Origin` 或 `Referer` 到达检查时会被表示为同主机同端口的 `http://`，`http://` 的则表示为 `null`（外来），因此同源规则在 :9090 上同样精确比较主机和端口。没有 HSTS。http 源无法设置或读取 `__Host-`（Secure）Cookie；会话存储是共享的，因此会话令牌只有在 Cookie 能到达相应源时才在那边有效，而浏览器并不会这么做。Cookie 不按端口隔离，因此同一主机上的其他 HTTPS 服务器（192.168.0.1 的 :443 上中兴的 uhttpd）可能设置或覆盖 `__Host-zte_ui_*` Cookie；Origin 和 CSRF 检查仍会拒绝其请求，因此它最多只能让浏览器退出登录（Cookie 投掷）。
- **偏好设置**（设置 › 轮询与外观，`web::prefs`）：`zte_ui_theme=light|dark` 和 `zte_ui_refresh=<ms>`，`Path=/ui/; Max-Age=31536000; HttpOnly; SameSite=Strict`，由经过 CSRF 校验的 POST 设置（没有一次性令牌：重复设置同值即可；表单未提供的值为 `400`）；默认值（跟随系统、2.0 s）会清除 Cookie。它们只保存固定值，属于浏览器而非会话（退出登录后保留）。与会话 Cookie 一样，第一个格式正确的值生效，因此同一主机其他端口用更深路径植入的 Cookie 只能在相同的值中选择。

## 变更与操作

- 每个变更都是路由表中的一个动作：带会话 CSRF 令牌的 POST；发送到设备的请求体只由校验过的值构成（超出其列表的值为 `400`）。设备错误会重新显示页面并带“失败：<error>”（已转义，最多 120 个字符）以及调用的状态。当动作要合并的状态无法读取时不发送任何内容：重新显示页面并带错误（`503`），绝不进入操作页面。
- 页面 GET 只读取；调试构建中，页面加载若调用变更类 API 路由会 panic（`httpd::gate::read_only`）。页面在其最慢读取所属的闸门通道中等待。
- **设备控制**（App 的 `DeviceControlView`；`pages::devctl`）在页面加载时读取（不建流：App 也只读一次）：`GET /api/device/charge-control`、节能模式（App 用 `POST /api/device/power-save` 读取它；页面直接调用 Agent 的对应处理函数，因此页面加载不会发送 POST）、`GET /api/device/fast-boot` 和 `GET /api/device/auto-sleep`。读取失败时显示 App 的“无法加载……设置”并附错误，其开关显示“不可用”以及开和关（App 会显示为关）；充电上限只显示“不可用”，不显示表单（否则其保存会用默认值覆盖路由器的值；App 在读取到之前不发送任何内容）。
  - **充电上限**：开关、“停在”（App 的滑块改为列表，50–100 %，步长 5；不在网格上的已保存值会排在最前）和“恢复间隔”（步进器改为列表，1–20 %），开关关闭时由 CSS 隐藏，以及“保存”（单个表单 `tabs::router::CHARGE_LIMIT`，使用页面的一次性令牌，因此双击只保存一次；App 每次变更都会立即发送）。无效值会重新渲染表单（`400`），数字时保留已输入内容，并按字段给出提示。保存后回到页面并读取新值（App 不显示提示行）。App 的页脚跟随已保存的值。
  - **节能模式、快速启动、自动休眠**：像 App 一样立即生效的开关，由页面携带其一次性令牌发送（`pages::confirm` 各类；双击只发送一次），请求体与 App 相同：`PUT /api/device/power-save {"deviceInfoList":{"power_saver_mode":"1"|"0"}}`、`PUT /api/device/fast-boot {"fast_boot":"1"|"0"}`、`PUT /api/device/auto-sleep {"enabled":true,"timeout":"<the router's>"}`（当路由器的值不在 1–1440 内时用 App 的默认值 "5"）或 `{"enabled":false}`。自动休眠开启时，“空闲超时”（5、10、20、30 分钟、1 小时、2 小时；其他路由器值会排在最前）配合“保存”会发送 `{"enabled":true,"timeout":"<n>"}`。随后回到页面，显示路由器回读的值（App 不显示提示行）；失败时显示 App 的“失败：<error>”。从远程浏览器开启自动休眠会先询问（Web 新增）：“打开自动休眠？”（“当没有 Wi-Fi 设备连接达到<超时>后，路由器会休眠。按电源键可唤醒。”/“你正在远程连接：路由器休眠期间，除非按下其电源键，否则无法访问本页面。”）。
  - **重启路由器、恢复出厂设置**（蓝色和红色按钮，带 App 的页脚）把 App 的 `PasswordConfirmView` 作为页面打开：App 的提示（“输入路由器密码以确认重启。”/“这将清除所有设置。输入路由器密码以确认。”）、“路由器密码”（页面从不预填；重启时浏览器可能填入 Agent 密码，而该密码就是它；恢复出厂设置的字段要求浏览器和密码管理器不要填充它，`autocomplete="off"` 及其忽略属性，因此重置始终是手动输入的、慎重的步骤）、红色的“重启”/“恢复出厂设置”（字段为空时由 CSS 变暗，如同 App 的禁用按钮）、会发生什么（页面页脚），以及对远程浏览器显示的远程说明（恢复出厂设置时：“……路由器可能不会回到你的 tailnet；届时只能在其 Wi-Fi 上的设备旁重新设置。”）。POST 与“需要重启”相同（见下文）：先在路由器上校验密码（App 用密钥链比较），再校验一次性令牌，然后 `POST /api/device/reboot` 或 `POST /api/device/factory-reset`，用页面本身作答（路由器可能不再响应重定向）：“正在重启……”并带 App 的“路由器正在重启……”、“路由器约一分钟后恢复。重启会让所有浏览器退出登录，因此你需要重新登录。”和“重新加载”（仪表盘）；“正在重置……”并带“已启动恢复出厂设置……”、Wi-Fi 名称、Wi-Fi 密码和地址将恢复出厂默认值，以及如果 Web UI 没有恢复，重置可能已移除 Agent。重放该 POST 会得到同一页面；失败时重新显示面板并带“失败：<error>”和调用的状态。
- **确认页面**（除下文所述的 WiFi、访客 WiFi、APN、局域网/DHCP、DNS、每项防火墙变更和被阻止域名的移除之外）还用于：关闭移动数据、打开漫游、打开飞行模式、每次网络模式变更（App 没有对话框；无覆盖的模式可能让远程浏览器失联，页面会告知）、远程浏览器关闭漫游时（对端为回环，即 Tailscale），因为这在国外可能切断连接、每次终止进程、启动测速（移动数据）、启用 ADB、每次锁定和解锁频段、App 认为危险或 Web 新增的 AT 命令（见 AT 终端）、手动注册、每次小区锁定和解锁、智能基站连接的启用、停用和重置白名单，以及远程浏览器开启自动休眠（App 对这些都不询问；每项都可能中断服务，远程浏览器会被告知）。重启路由器、恢复出厂设置和“需要重启”的“立即重启”是 App 的密码面板，在路由器上校验。SIM 卡的面板是独立问题（PIN 在提问页面上输入）：启用/停用 PIN 锁、更改 PIN 和输入 PUK 会说明会发生什么以及出错的代价，并附远程说明（每段远程说明以“你正在远程连接：”开头，然后说明在此处的含义：`confirm::REMOTE`“……如果连接中断，在路由器重新上线之前无法访问本页面。”；关闭移动数据和打开飞行模式“……这会切断连接，在路由器上重新打开之前无法访问本页面。”；网络模式“……如果 <模式> 在此处没有覆盖，……直到在路由器上更改模式。”；关闭漫游“……如果路由器在国外，……直到在路由器上重新打开漫游。”；打开防火墙或提高级别“……如果防火墙阻止了此连接，请从路由器 Wi-Fi 上的设备改回。”；局域网/DHCP 的应用使用 `confirm::REMOTE` 那一行（路由器网络会重启）；打开自动休眠“……路由器休眠期间，除非按下其电源键，否则无法访问本页面。”；恢复出厂设置“……恢复出厂设置后路由器可能不会回到你的 tailnet；……”；终止启动关键守护进程“……如果路由器停止响应，在它重启之前无法访问本页面。”）。漫游现在属于移动网络的应用（与 App 一致）：打开时会询问，关闭时只对远程浏览器询问。
- **进程**：每次终止都在点名守护进程的页面上确认（App 终止单个进程时不询问）。PID 只能是数字，1–4194304，否则 `400`。表单提交 PID 和该名称（必须是 Agent 预装软件名单之一，否则 `400`）；除非该 PID 仍在运行该守护进程（PID 会被复用，而问题页面可能停留数分钟），POST 不发送任何内容：“PID 812 已不再是 zte_topsw_diag。未终止任何进程。” Agent 回答中未列为已终止的 PID 会得到“PID 812 未被终止。”（两者均为红色），绝不用 App 的提示行。单个终止只在预装软件行上提供，且对所有预装守护进程始终可用；页面对 `zte_topsw_wms`（SMS 会停止，包括本 UI 的短信标签页和转发，直到它重启）以及 daemon.conf 成员（启动关键；对远程浏览器再加一行）给出警告。**终止全部预装软件**在 Web 上绝不会终止这些（所有者决策）：它会列出将终止和保持运行的项，POST 会重新读取 `/proc`，只对其他预装守护进程发送 `{"pids":[…]}`（绝不发送 `{"all":true}`）；若没有正在运行的，则不发送任何内容，结果行为中性提示：“没有正在运行且可安全终止的预装守护进程。未终止任何进程。” Agent 会再次核对每个 PID 的名称是否在其预装软件列表中。当列表中存在它愿意终止的预装守护进程时才会显示“终止全部预装软件”：当所有预装守护进程都属于它保留运行之列且全部出现在列表中（列表按 CPU 取前 50）时隐藏；不在列表中的预装守护进程会保留该链接，但其页面随后可能显示“没有正在运行且可安全终止的预装守护进程。”且只有取消。结果（“已终止 PID 812，释放 1.2 MB”、“已终止 3 个守护进程，释放 8.4 MB”，绿色，与 App 一致）根据 Agent 的回答生成，只为发起请求的会话保留（每会话最多 8 条，总共最多 64 条，保留 10 分钟；其他会话的行永远不会把它挤掉），并通过 `?r=<id>` 在列表上显示（每次加载该 URL 时），位于内容上方，与所有提示一致（App 在预装软件摘要之后显示）。
- **USB-C 卡片**：“快速充电”提交 `state=1`，这是唯一接受的值（其他值为 `400`）；Web 发送 `{"state":1}`（API 会把请求体不加校验地交给 ubus），且只在读取到已插入线缆后才发送（在拔线之前显示的页面会得到“失败：未连接 USB-C 线缆。”，`503`，且不发送任何内容）。与 App 一样无需确认。移动电源模式是否会中断使用同一线缆做 USB 联网的电脑，尚未在设备上验证。成功时显示“已启用快速充电”（绿色，`?r=<id>`），失败时仪表盘显示“失败：<error>”（App 无论如何都会关闭面板，因此看不到其失败消息）。关闭快速充电属于工具 › USB 模式，与 App 一致。“关闭”不发送任何内容：它为本次会话设置一个标志（在内存中，最多 16 个会话，各一天）并返回仪表盘。
- **工具 › USB 模式**（App 的 `USBModeView`）：“USB 状态”（线缆“已连接”/“已断开”、USB-C CC、模式）和带 App 页脚的“快速充电（移动电源）”开关，在页面加载时读取（不建流）。开关只提交 `state` 0 或 1（否则 `400`），Web 构造 `{"state":0|1}`；与 App 一样，未插入线缆时禁用。结果：“已启用快速充电”/“已关闭快速充电”（绿色，`?r=<id>`）。
- **网络模式**：只接受 App 的六个值（`WL_AND_5G`、`LTE_AND_5G`、`Only_5G`、`Only_LTE`、`WCDMA_AND_LTE`、`Only_WCDMA`）；其他值返回 `400` 且不发送任何内容（API 会把请求体不加校验地交给调制解调器）。表单还会提交它当时显示为当前的模式；应用同一模式不会改变任何东西，与 App 的禁用应用一致。
- **自动化**（App 的 `SchedulerView`）：Agent 调度器任务，在页面加载时读取（不建流：App 只在下拉刷新时重读，已运行的任务在下次加载时显示）。每行：名称、App 的调度摘要（“每天”、“周一至周五”、“周末”或具体星期几、“ at HH:MM”、“ → HH:MM”并带恢复；“一次性：2026 年 10 月 23 日下午 3:41”，按路由器时区；无日期时为“一次性”）和动作摘要（模板标签，否则为“METHOD path”）、开关（`{"id","enabled"}`，与 App 一致；返回该行，`#j<id>`）、最近一次运行后的圆点（在开关下方，与 App 一致：成功为绿色，否则红色，供屏幕阅读器使用“最近一次运行成功”/“最近一次运行失败”）和“删除”（App 会立即删除）：“删除“<名称>”？”，以及“它将不再运行。”，若有恢复则再加“它在 HH:MM 的恢复也不再运行，因此如果动作已经执行，就没有任何东西会撤销它。”。然后 `DELETE /api/scheduler/jobs {"id"}` 和“自动化已删除”。删除一次只运行一个（读取与调用）。问题页面显示的任务若已消失，则不发送任何内容：双击、第二个标签页或重放也会落到“自动化已删除”，绝不会出现“任务未找到”。任务不存在时显示：“未找到自动化。它可能已被删除。”并只有取消（`404`，与编辑自动化一致）。没有任务时：App 的“没有自动化”文案；读取失败时：其上方显示“加载失败：<error>”（与 App 一致）。Agent 给新任务的 id 是当前最大 id 加一，因此已删除的最新任务 id 会被复用：开关、删除问题和新建/编辑自动化都会随 id 携带任务的创建时间（`c`），且只作用于页面显示的那个任务（那里是另一个任务时：“失败：任务未找到”或“未找到自动化”，不做任何更改）。远程浏览器会在“动作”下方看到：“你正在远程连接：飞行模式开和移动数据关在运行时都会切断此连接。打开“在……反向动作”可恢复。”（立即开关会先询问；计划任务无法询问）。App 解析器丢弃的任务（缺少 id、名称、开关、调度类型、方法或路径）会被排除。提示使用 App 的措辞，绿色与 App 一致；失败为“失败：<error>”（例如“失败：任务未找到”）。

- **添加 eSIM**（App 的 `RouterESimAddView`，基于 Agent 的下载 API，[esim.md](esim.md#download)）：
  - **入口**（没有下载运行时）：App 的页头（“向你的路由器添加配置文件”及其文本）、页面加载时数据调用不可用时显示其“你的路由器没有移动数据连接……”说明，然后一个表单：“扫描二维码”（文件输入，带 `capture="environment"`：手机浏览器会打开相机）、“从照片选择二维码”（文件输入；两者均为 `accept="image/jpeg,image/png"`，按钮下方显示所选文件名）、“手动输入代码”（一个 `<details>`，内含密码字段“LPA:1$…”）、“运营商确认码”（一个 `<details>`，内含密码字段和 App 的页脚；App 只对需要确认码的代码显示该字段，而无脚本页面在提交前无法知道：当代码要求时它才展开）和“读取配置文件详情”（切换运行时禁用，并显示 App 的忙碌提示）；然后是 App 的两个页脚。两个字段都是 `autocomplete="one-time-code"`（浏览器会忽略密码字段上的 `off`，可能提示保存；Chromium 和 WebKit 不会提示保存一次性代码；未在每个浏览器中检查），并带密码管理器的忽略属性，且始终绘制为空。确认码的页脚是 App 的；其摘要写着“(如果有的话)”。
  - **提交**（`multipart/form-data`，`web::upload`）：先检查会话和同源，再读取请求体，之后检查 CSRF 令牌；一次只允许一个上传（另一个最多等待 10 s，然后显示忙碌页面）；照片最多 8 MiB（否则 `413`“照片过大”，并在读取任何内容前按声明的长度拒绝），暂停 15 s 或总计两分钟为 `400`；文本字段最多 1 KiB，最多 8 个部分。只能有一个输入：照片（任一文件输入）或代码（两者都有或都没有：会有一行提示）。App 的校验（`RouterESimActivationCode`）：去除空白，最多 512 字节，`LPA:` 和 3 到 5 个 `$` 部分，第一部分为 `1`，服务器部分 `[A-Za-z0-9.:-]`，matching ID 为 `[A-Za-z0-9-]`，第五部分为 `1` 时要求确认码（1 到 64 字节，无控制字符）。App 的措辞：“此二维码不是 eSIM 激活码。”、“请选择只含一个 eSIM 二维码的照片。”、“无法读取此照片。请选择其他图片或手动输入代码。”、“请输入运营商的确认码（最多 64 个字符）。”；Web 新增的提示用于无输入、两个输入、既非 JPEG 也非 PNG 的图片、过大而无法解码的图片以及解码器忙。每次拒绝都会加上“你的代码不会被保留，因此请重新扫描、选择或输入。”（代码绝不会回填到表单）。
  - **然后，携带页面的一次性令牌**（慢速通道；其摘要使用进程密钥做 HMAC，因此令牌存储中不保存代码的明文哈希；未发送时归还）：照片会被解码（`web::qr_decode`：在子进程 `zte-agent qr-decode --child` 中，一次一个，15 s 后杀死，从而立即释放解码器；照片字节通过管道传给它，随后丢弃），并检查其中的二维码（一个激活码；同一个出现两次只算一次）；切换或下载占用 eSIM 时不会启动任何内容（“eSIM 正忙；请稍后再试。”）；然后 `POST /api/esim/download {"activation_code","preview":true[,"confirmation_code"]}` 并 `303` 到下载卡片。Agent 的拒绝（无移动数据、卡片忙、SIM 重新加载、不同的卡片）显示在 App 的“无法开始此下载”卡片中（其忙碌 409 显示为 App 的忙碌提示；“无移动数据”附 App 的说明）。
  - **下载卡片**（`#eadd-dl`；App 的 `downloadContent`）：App 的进度行（“正在连接运营商……”、“正在读取配置文件详情……”、“正在下载配置文件……”、“正在安装到 eSIM……”、“正在准备 eSIM……”、“正在取消……”）带转圈图标及其说明（“请保持路由器联网。你可以关闭此屏幕并稍后返回查看进度。”，安装期间为“请保持路由器通电。此阶段无法取消安装。”）；预览：“可以安装”、“安装 <提供商或名称>？”、不同时显示配置文件名称、“该配置文件将安装到路由器的 eSIM 上，并在你切换到它之前保持停用。请在 2 分钟内确认。”和“安装配置文件”（Agent 会在 2 分钟后取消未答复的预览）；App 提供时可用的“取消下载”（运行中或预览阶段，安装期间不可用）。完成：“<名称> 已添加。”、“已添加到你的路由器。当前配置文件仍处于活动状态。”、“立即切换”（该配置文件的 eSIM 配置文件切换问题，`switch?new=1`：其警告、远程说明，然后切换的操作页面）和“稍后”（返回 eSIM 配置文件）。失败：“无法添加配置文件”、Agent 的错误（或“运营商无法添加此配置文件。”；含 `$` 或 `LPA:` 的单词显示为“…”以防运营商服务器回显代码）和“重试”（回到添加 eSIM，“手动输入代码”展开，与 App 一致）。已取消（App 会返回其入口）：“下载已取消”、Agent 说明时显示“未在 2 分钟内确认。”以及“添加 eSIM”。下载运行期间从 `esim_download` 实时更新，等待其回答或取消；没有 JavaScript 时，运行或取消期间页面每 3 s 重新加载（等待“安装配置文件”时不重载）。
  - **安装配置文件和取消下载**是片段之外表单 `#eaddf` 的按钮（与 SIM 服务一致），每次提交都带页面的一次性令牌：会重新读取下载状态，当它不再等待回答或无法再取消时不发送任何内容（卡片随后显示其当前状态）；然后 `POST /api/esim/download/confirm {"accept":true}` 或 `POST /api/esim/download/cancel {}` 并 `303` 到卡片；Agent 的拒绝显示为 App 的下载提示（橙色，带“检查状态”）。
  - **Web 未提供**：App 的摄像头扫描器（其取景框、手电筒和说明；改由浏览器相机或文件选择器拍照，在路由器上解码）和“正在读取照片……”（提交会等待解码）。安装时没有远程说明：安装不会触碰连接；切换问题才有。
- **SIM 服务**（App 的 `STKMenuView`），只通过 Agent 的路由（`/api/ussd/*`、`/api/stk/*`；Agent 的工具包工作线程持有 RIL 套接字）：
  - **USSD**：“USSD 代码（例如 *100#）”及发送（App 的页脚），然后显示“响应”（`response`，否则 `raw_response`），并且在网络保持会话打开期间（`session_active`）显示“回复”和“结束会话”。代码和回复可包含数字、`*`、`#` 和 `+`（空格会被丢弃；“USSD 代码只能包含数字、*、# 和 +。”，Web 新增：Agent 会丢弃其他字符）；为空时显示 App 的“请输入 USSD 代码”；空回复不发送。调用与 App 相同（`POST /api/ussd/send {"code"}`、`…/respond {"reply"}`、`…/cancel`，慢速通道，Agent 最多等待 8 s）。每个结果（回答、“USSD 会话已结束”（绿色）、“失败：<error>”，后者会像 App 一样保留所显示的回答，发送失败也一样：其表单携带回答的 `u`）会在会话的内存中保留（`store::UssdLog`：最多 8 条，10 分钟，退出登录后清除），按提交的一次性令牌索引并通过 `?u=<token>` 显示，因此双击只发送一次，两者都落到同一回答；字段保留代码。回答原样显示（与 App 一致，例如完整的代金券号），截断到 4 KiB。带有 PIN 或 PUK 的标准 SIM 代码（`**04*`、`**042*`、`**05*`、`**052*`：更改 PIN、用 PUK 解锁）会被拒绝，这是 Web 新增：作为 USSD 发送会把 PIN 等一并送到网络，绕过 SIM 卡的校验（“请使用 路由 › SIM 卡 更改 PIN 或输入 PUK。”，字段清空）。
  - **SIM 工具箱**：普通加载页面会打开工具包会话（`GET /api/stk/menu`，对应 App 打开屏幕时的加载及其“重新加载 SIM 菜单”；`Screen::before`，因此随后读取的 `stk` 主题会显示它）；USSD 回答（`?u=`）或结果行（`?r=`）不会。操作失败后（`held=1`）页面显示 App 的失败状态（其 `failSTK`）：“SIM 工具箱”、“重新加载 SIM 菜单以重新连接。”以及只有“重新加载 SIM 菜单”，不显示工作线程可能仍持有的菜单（第二次点击可能重复一次购买），不建流也不自动重载，直到重新加载。否则页面跟随 `stk` 主题（工作线程状态 `GET /api/stk/session`，从工作线程内存读取）：标题（否则“SIM 工具箱”）、原因和文本、每个菜单项一个按钮、“是”/“否”、“继续”（显示型）、返回和结束 SIM 会话（根菜单下方）、重新加载 SIM 菜单（无菜单时；指向页面的链接）、App 的页脚“来自 SIM 卡的运营商提供服务”；SIM 忙时（`busy`）按钮变暗，没有 JavaScript 时页面每 3 s 重新加载。按钮属于片段之外的同一个表单（`#stkf`：CSRF 和一次性令牌），各自指定命令和项目（`c=<command_id>.<item>`），因此实时到达的菜单无需重新加载即可工作，而过期菜单会被 Agent 拒绝（"stale or missing command_id; reload the SIM menu"）。SIM 要求的文本（“SIM 响应”，SIM 隐藏时用密码字段，“输入 min–max 个字符”，“发送响应”）是片段之外的另一个表单，按页面加载时的命令绘制（另一命令出现后由 CSS 隐藏）；实时到达的表单会提供“输入响应”，点击后重新加载。App 的请求体：`POST /api/stk/select {"command_id","item_id"}`、`…/respond {"command_id","text"[,"yes"]}`、`…/back`、`…/cancel {"command_id"}`（慢速通道）。成功后回到页面，显示 SIM 接下来做什么；失败为 `?held=1` 处的“失败：<error>”（红色），与 App 一样在那里停止（绝不重试：超时的选择可能已到达 SIM）。工具包文本原样显示，与 App 一致。一次性令牌每页一个，由其表单共用（每次提交都会进入新页面）。工具包最多分布在三张卡片中（区块、响应表单、返回/结束 SIM 会话/重新加载及页脚；App 只有一个区块），因为片段无法容纳表单。
- **短信**（App 的消息和会话）：消息中未读的行是一个单按钮 POST 表单（`/ui/sms/open`）：它只把该会话的未读消息标记为已读（`{"id":"<ids>;","tag":0}`，失败时静默，与 App 一致）并打开该会话；已读行是链接。GET 绝不标记任何内容；从链接打开且含未读消息的会话会提供“标记为已读”。列表无法读取的会话会显示原因并带“重试”，且没有回复栏（没有可回复的对象）；回复失败的回应会保留其栏和文本。会话 URL 的键是其发送者的 HMAC（每进程随机密钥，16 个十六进制字符），因此链接在 Agent 重启前有效（之后显示“找不到会话”）。
- **短信回复**：文本不得为空，且不超过 765 个 GSM-7 字符或 335 个 UTF-16 单元（Web 新增；App 不校验）；请求体与 App 相同（`message_body` 始终为 UCS-2 十六进制，`encode_type` 按字符集，`sms_time` 为路由器时区，`id` 为 "-1"），在发送时从键解析出会话号码；设备的 `result` 必须为 3（数字或字符串）或缺失，否则为“发送失败：设备拒绝（result=N）”（API 路由不做检查）。每个带回复栏的页面都会携带新的一次性令牌（`autocomplete="off"`，因此浏览器不会把它恢复到表单的旧副本中）。存储在所有会话间最多保留 64 个令牌，各一小时；写满时，正在发送的令牌绝不会被淘汰：先淘汰提交会话最旧的未使用令牌，再是其已使用的令牌，最后是其他会话的。提交会先检查令牌；只有在调用前、文本有效时才占用，并附带目标号码和文本的哈希（绝不保存文本），未发送时归还（路由器忙、列表不可读、会话已消失、请求在等待路由器时被丢弃、调用前的工作 panic）。用已占用的令牌再次提交同一次发送（双击、重载回答）不会发送：它会等待第一次的结果（最多 20 s）并显示其所作所为，即会话或其失败；若仍未知（仍在发送，或令牌已消失），显示会话及文本和“此消息可能未发送。再次发送前请检查会话。”（409）。令牌配其他文本或号码（表单的旧副本）、未知令牌或已过期令牌会显示“此表单已过期，因此消息未发送。请重新发送。”。每次失败都会重新显示会话并保留文本，与 App 一致；路由器忙时，不读取内容的页面只显示回复栏、文本和“发送失败：路由器忙。请几秒后重试。”（503）。回复栏是页面的 `#end`：进入会话的链接和发送失败的回应都会落到它上面，失败提示行就在字段正上方。
- **新建消息**（`SMSComposeView`）：号码（`type=tel`；先去除手机键盘和自动填充带来的空格、`-`、`(`、`)` 和 `.`，然后最多 32 个数字、字母、`+ * #`；Web 新增，App 原样发送输入内容）、带 App 计数器的正文（“<长度>/<上限>（<n> 条短信）”，为空时“0/765（0 条短信）”，在绘制页面时计数：没有 JavaScript 就没有实时计数器）、发送（字段为空时变暗，与 App 禁用一致），然后失败提示行。它提交到 `/ui/sms/send`，令牌规则与回复相同。已发送：消息页显示“消息已发送”（Web 新增）。重放已占用令牌且第一次提交结果未知（20 s 后仍在发送，或令牌已消失）时，会进入消息页但不显示“消息已发送”。被拒绝时重新显示表单并保留两个值和新令牌；路由器忙时同样显示，并带“发送失败：路由器忙。请几秒后重试。”（令牌归还）。
- **删除会话**（App 的滑动，会立即删除；Android 对话框的措辞）：“删除会话？”/“这将删除来自 <号码> 的全部 <n> 条消息。”/删除、取消。号码只出现在页面中；URL 只携带键，`<title>` 为“删除会话？”。表单携带会话指纹（消息数和新消息 id）。POST 会重新读取会话，若指纹变化（收到新消息），则以“会话已变化。请查看后重试。”再次询问（409），因此绝不会在未查看的情况下删除。然后 `POST /api/sms/delete {"id":"<每个 id>;"}`，与 App 一致。已删除：消息页显示“会话已删除”（Web 新增）。失败：消息页显示“删除失败：<error>”（App 的措辞），作为本次会话的结果行（`?r=<id>`），因此页面是一个 GET，其链接和流都能工作。没有 `confirm=1` 的 POST 会进入问题页面。某个存储无法读取时（“全部”且 SIM 不可读），不会删除任何内容，因为它可能还存有该会话的更多消息：问题页面显示读取错误而非表单，提交会得到“删除失败：无法读取 SIM 消息：……”（“内部”或“SIM”过滤会从可读取的存储中删除）。
- **短信转发**（App 的 `SMSForwardConfigView`）：“设置”及“启用”（立即生效的开关，与 App 一致）和“转发后标记已读”、“转发后删除”开关及“保存设置”（“设置已保存”）；然后是规则（或 App 的“没有规则”文案）、“新建规则”、“转发日志”，以及至少转发过一条消息后的“最后转发的 ID”。配置在页面的闸门任务中读取，其机密在任何内容渲染前被丢弃（`web::forward::public`）。两次写入都发送 App 的请求体 `{"enabled","poll_interval_secs","mark_read_after_forward","delete_after_forward"}`，用提交时的配置构建（轮询间隔原样回传；Web 没有对应字段，与 App 一致）；读取失败则不发送（`503`）。规则行显示 App 的摘要（“所有消息”、“发送者：a, b”、“关键词：x”、“发送者：… + 关键词：…”、“Telegram（会话：<id>）”、“SMS（<号码>）”、“ntfy（<主题>）”、“Discord”、“Slack”），但 webhook 只显示其主机（“Webhook（example.com）”；App 显示完整 URL）。其开关提交 `{"id","enabled"}` 并返回该行（`#r<id>`）；“删除”会询问“删除“<名称>”？”，（App 会立即删除）：新消息不再经它转发，它在连接恢复前暂存的转发会被丢弃（由 Agent 结算），其日志条目保留。已删除：“规则已删除”。规则不存在时：“未找到规则。它可能已被删除。”并只有取消（`404`，与编辑规则一致；规则无法读取时为 `503`）。提示使用 App 的措辞，绿色与 App 一致；失败为“失败：<error>”（例如“失败：找不到规则”）。
- **新建规则/编辑规则**（App 的 `SMSForwardRuleFormView`）：“名称”、“过滤”（四种类型作为分段选择，使用它们的类型由 CSS 显示“发送者模式（逗号分隔）”和“关键词（逗号分隔）”；没有 `:has()` 时所有字段都显示）、“目标”（六种类型；每种类型的字段来自同一张表 `web::forward::DESTS`，它也驱动解析、校验和传输格式；CSS 显示所选类型的字段，服务端只读取这些）、“测试目标”、“保存”（名称为空时变暗，与 App 禁用一致；服务端无论如何都会校验）。新建规则不读取任何内容，因此路由器忙时也能显示。规则的其他值会填充表单；其他类型保留空白表单的默认值（ntfy 的 `https://ntfy.sh`），与 App 的草稿一致。校验（Web 新增；App 只禁用按钮）：名称（最多 100 个字符）、以 `http://` 或 `https://` 开头的 URL、ntfy 主题只含字母、数字、`-` 和 `_`、转发号码同新建消息、头名称符合 HTTP token；不得含控制字符。ntfy 服务器 URL 只能是服务器本身（不得含 `?` 或 `#`：Agent 会追加 `/<主题>`）。App 保存的无协议 URL 会显示其主机（“Webhook（example.com）”）且需要重新输入：“保存的 URL 不以 https:// 或 http:// 开头。请重新输入。”。每条消息显示在其字段下方，顶部显示“请检查高亮的字段。”（`400`）。在字段中按回车会保存而不会测试（隐藏的保存按钮排在前面）。

  - **防火墙**：“防火墙”（状态，已启用为绿色/已停用；“停用防火墙”/“启用防火墙”；启用时显示“级别”低/中/高，各指向其问题的链接；“WAN Ping”已阻止/允许）、“NAT / UPnP”（开关；UPnP 读取失败时显示“不可用”及两个方向，而 App 显示为关）、“DMZ”（“启用 DMZ”、“DMZ 主机 IP”在开启时由 CSS 显示、“应用 DMZ”：草稿表单，同 WiFi）、“端口转发”（“启用”；开启时显示“添加规则”（App 的蓝色按钮行）和规则：名称或“规则”、活动为绿色/非活动、“TCP WAN:8080 → 192.168.0.50:80”、垃圾桶按钮）、“MAC/IP/端口过滤”（只读，与 App 一致；仅在有内容时显示）。防火墙读取失败时只显示 App 的“加载防火墙失败：……”；规则读取失败会在其区块中说明。新建端口转发（草稿表单）：规则（名称、协议 TCP / UDP / TCP + UDP）、WAN（WAN 端口）、LAN（LAN IP、LAN 端口）、“添加规则”（端口或地址为空时变暗，与 App 的禁用按钮一致）。每次变更都先询问（App 不询问：每项都可能把设备开放到互联网或切断对它们的访问）：“关闭防火墙？”和降低级别（两者都带“路由器其他服务，如 2222 端口的 SSH 和固件自带网页，可能从移动网络访问到。本 Web UI 和 Agent 的 API 仍会拒绝来自移动网络的连接。”：Agent 自己会拒绝移动侧，见[请求处理流程](#请求处理流程)；当 `ZTE_AGENT_ALLOW_MOBILE=1`，或 Agent 的接口查找失败时，旧提示为“路由器本身（包括本 Web UI）可能从移动网络访问到；届时只有 Agent 密码保护它。”）；“打开防火墙？”和提高级别（“……这可能切断对路由器或其上设备的访问。”，以及远程说明）；降低级别；NAT、UPnP 和端口转发的开与关（“N 条规则把互联网端口开放到路由器的设备。”）；“把……设为 DMZ 主机？”/“关闭 DMZ？”（已如此时“无需应用”）；“添加“…”？”（“……设备的该端口可从互联网访问。”，以及“端口转发已关闭：规则将在打开后生效。”）；“删除“…”？”。校验（Web 新增；App 只需输入端口和地址）：端口 1–65535；LAN IP 和 DMZ 主机必须是路由器子网内设备的地址（不能是路由器自身地址，否则会把自身服务开放到互联网，也不能是网络地址或广播地址；无法读取路由器网络时一概不接受：“无法读取路由器的网络。请重试。”）；另一条规则已为重叠协议转发的 WAN 端口会被拒绝（“WAN 端口 8080 已被转发。”）；名称最多 32 个字母、数字、空格、点、连字符和下划线。删除会指明其来源列表（`g`，列表的哈希）：在某些固件上规则 id 是列表位置（App 的回退），因此列表一旦变化，问题页面就不提供任何操作，提交也不发送任何内容（App 的“规则列表已过期并已重新加载。请重试。”）。App 的提示行：“防火墙已启用”/“已停用”、“防火墙级别已设为高”、“NAT ……”、“UPnP ……”、“DMZ 设置已更新”、“端口转发 ……”、“端口转发规则已添加”/“已删除”。与 App 一样，规则不可编辑，过滤器不可更改（Agent 没有对应固件 `router_set_macipport_filter` 的路由）。
  - **线上名称**（未在设备上验证）：固件 `ubus -v list` 的字段名与 App 发送的不同（`router_set_firewall_switch {"enable"}`、`router_set_firewall_level {"level"}`、`router_set_nat_switch {"enable"}`、`router_set_upnp_switch {"enable_upnp"}`、`router_set_dmz {"dmz_enable","dmz_ip"}`、`router_set_portforward_switch {"portforward_enable"}`、`router_set_portforward {"action","section_id","src_dport","proto","dest_ip","enabled","comment"}`、`router_set_domain_filter {"action","section_id","enable","fqdn"}`、`router_set_lan_para {"ipaddr","netmask","ignore","zte_start","zte_end","leasetime","other"}`），因此请求体同时携带 App 的键和同一设置的固件键，其整数以整数形式发送（与小区锁定、STC 使用固件名称一致）；固件的端口转发没有 LAN 端口（App 的 `lan_port` 原样发送）。局域网/DHCP 同时发送 App 的键（`lan_ipaddr`、`lan_netmask`、`dhcp_enable`、`dhcp_start` 为 Agent 读取的偏移量、`dhcp_end`、`dhcp_lease_time`）和固件的键（`ipaddr`、`netmask`、`ignore` 关闭 DHCP 时为整数 1、`zte_start` 和 `zte_end` 为地址、`leasetime`）；固件的反汇编从这两个地址推导 UCI 的 `start` 和 `limit`。读取优先用 App 的名称，否则用固件的 UCI 名称（`firewall_enable`、`nat_enable`、`dmz_enable`、`level`、`wan_ping_enable`（开启：可应答，故为“允许”；推断）、`portforward_enable`、`enable_upnp`；规则的 `section_id`、`comment`、`proto`、`src_dport`、`dest_ip`、`dest_port`；域名的 `fqdn`）。该列表没有 `router_get_upnp_switch`、`router_get_qos_switch` 或 `router_set_qos_switch`（只有 `router_get_upnp`、`router_get_qos`、`router_set_qos`），也没有透传开关（`router_set_alg_switch` 只接受 `alg_sip_enable`），而 Agent 的路由会调用它们：在此固件上，UPnP 状态、QoS 和 VPN 透传可能只显示路由器的错误，与 App 一致（Agent 后续）。
  - **遥测拦截**：“域名过滤”（状态、“停用过滤”/“启用过滤”）、“快捷操作”（“拦截全部中兴遥测”和 App 的五个已知域名：已拦截时显示绿色对勾，否则灰色圆圈；屏幕阅读器为“已拦截”/“未拦截”）、“添加自定义域名”（“要拦截的域名”、“添加”，为空时变暗）、“已拦截域名”（活动/非活动、垃圾桶按钮）。开关、添加和全部拦截由页面携带其一次性令牌提交，与 App 的按钮一致；移除会先询问（“移除 ads.example.com？”、“路由器上的设备将能再次访问 ads.example.com。”）并像端口转发的删除一样指明其列表。添加接受小写主机名（App 的“请输入域名”，然后“请输入 ads.example.com 之类的域名：字母、数字、连字符和点。”；被拒绝时按原样重新显示页面，`400`），已拦截的域名不发送任何内容（“ads.example.com 已被拦截”）。全部拦截只添加缺失的已知域名，每个一次调用，失败后继续（与 App 一致）：“已拦截 N 个遥测域名”、“所有遥测域名均已被拦截”，或“已拦截 N 个遥测域名；M 个无法添加。失败：……”（App 对失败什么都不说）。App 的提示行：“域名过滤已启用”/“已停用”、“已添加……”、“已移除……”；读取失败：“加载过滤器失败：……”。
  - **VPN 透传**：L2TP、PPTP、IPSec（表单中的开关）和应用，由页面携带其一次性令牌提交（不询问任何内容，与 App 一致）：App 的请求体（`l2tp_passthrough`、`pptp_passthrough`、`ipsec_passthrough` 为 "1" / "0"）和“VPN 透传已更新”。读取失败时只显示“加载 VPN 失败：……”（App 会显示所有开关为关，应用会把它们全部关闭）。**QoS**：“服务质量”及“启用 QoS”（单按钮表单，立即生效，与 App 的开关一致）：`{"qos_switch"}`、“QoS 已启用”/“已停用”；读取失败显示“加载 QoS 失败：……”，开关显示“不可用”及两个方向。
- **一次性令牌**（`store::Once`）守护每个提交会执行不可重复动作的表单：回复、新建消息、规则的保存和测试、重试、自动化的保存、网速测试的开始、启用 ADB、频段锁定的应用和解锁、AT 命令，以及路由器相关变更：移动网络的应用、扫描和注册、小区锁定的锁定、解锁和邻区扫描、智能基站连接的启用、停用和重置白名单、信号检测的开始和停止、需要重启的“立即重启”、设备控制的充电上限、开关、空闲超时、重启路由器和恢复出厂设置、SIM 卡的各面板、SIM 服务的 USSD 和工具包提交、eSIM 配置文件的切换、删除、重命名和立即发送、添加 eSIM 的读取配置文件详情、安装配置文件和取消下载，以及 WiFi、访客 WiFi、APN、局域网/DHCP、DNS、防火墙、遥测拦截、VPN 透传和 QoS 的每次变更（WiFi、访客 WiFi、APN、局域网/DHCP、DNS、DMZ 和新建端口转发的草稿按令牌保留）。由此类提交启动的操作页面以该令牌作为 id，因此重放提交会进入同一页面。每个带此类表单的页面都携带新的随机令牌，每页一个、由其表单共用（`PageData::once`；`autocomplete="off"`；每次提交都会进入新页面）；无 JavaScript 时自行重新加载的页面（信号检测、SIM 服务）在未使用时保留其令牌（`?t=`），因此重新加载循环不会产生新令牌。存储在所有会话间最多保留 64 个，各一小时；写满时，正在发送的令牌绝不会被淘汰：先淘汰已使用的令牌（本会话的，再是其他会话的：它只能识别重放），然后淘汰持有最多令牌的会话中最旧的未使用令牌（并列时为提交方），因此持有较少令牌的会话（包括新页面）会保留它们。提交会先检查令牌（未知、过期或其他会话的：“此表单已过期……”/“此页面已过期，因此没有重试任何内容。请重试。”，不发送任何内容），然后检查字段，并在设备调用前用发送内容的哈希占用它；未发送时归还（路由器忙、读取失败、等待时请求被丢弃、工作 panic）。用已占用令牌的第二次提交不发送任何内容：同一提交会等待第一次（最多 20 s；测试或重试为 30 s，它们可能为慢速通道等待 7 s、为目标等待 15 s）并显示其结果；用它的其他提交视为过期表单。
- 没有 JavaScript 时，等待中的进度页面每 3 s 重新加载（`<noscript><meta http-equiv="refresh" content="3">`）；测试运行期间的网速测试和扫描运行期间的信号检测会重载到带观察点的自身 URL（`content="3; url=…"`）。
- 最多保留 8 个操作，每个按启动时钟保留 10 分钟，且仅限启动它的会话。

## 实时更新

- 实时页面只有一个 `data-init`，在页面可见后打开流。页面隐藏时 Datastar 关闭它，再次显示时打开新的。每次页面加载都有自己的流 URL，因此重连只替换它自己更早的流。
- 第一帧携带页面的所有片段；之后只发送 HTML 发生变化的片段（最多每 250 ms），外加 1 s 后的一次心跳，然后每 5 s 一次。
- 心跳会重启一个 CSS 动画：15 s 没有心跳后页面显示“15 s 无更新 · 刷新”。不涉及脚本定时器。
- 仪表盘的状态是导航栏胶囊：没有 JavaScript 时为“快照”（重新加载链接），并在年龄标记处由 CSS 显示“超过 1 分钟”/“超过 5 分钟”；心跳到达时显示“已连接”；15 s 无心跳后显示“离线”（重新加载链接）。App 的胶囊显示登录状态；在 Web 上，流是更接近的对应物。年龄标记（“4 秒前”）随每次读数和心跳移动，且仅在实时时显示（快照的标记永远不会动）。在仪表盘上它从最后一次成功信号读数起算（App 的只在刷新应答时移动）；在连接与信号上从最后一次读取起算，无论成败（与 App 的面板一致）。
- 仪表盘的卡片不显示年龄（与 App 一致）；主题读取失败的卡片显示“无法更新：<error>”（Web 新增）。流量说明的年龄从最后一次成功采样起算。各面板的年龄行在主题超过 3 个节奏后出现。
- 结束状态显示在状态行（仪表盘：胶囊中的“离线”，导航栏下方的结束原因）：已退出登录（带登录链接）、“已在另一个标签页打开”（一个会话的第四条流会替换最旧的一条）、路由器待机，以及“实时更新在 30 分钟后暂停”并带恢复。
- **刷新间隔**（设置 › 轮询，App 的滑块：1.0–10.0 s，步长 0.5 s，默认 2.0 s）：本浏览器的实时页面按该信号节奏向事件中心请求（`signal_hint`，如同 App 的 `signal_ms`；事件中心只对 `signal` 使用它，且最快的打开流生效）；自带节奏的页面（eSIM 配置文件的 10 s）保持自己的节奏。没有打开页面时它不改变任何东西：页面加载照常读取一次。App 的页脚仍然成立：流量每秒读取。
- 实时页面与 `GET /api/events` 共享事件中心的 8 条流，每个打开的实时页面各占一条；全部占用时页面显示“实时更新忙（打开的页面过多）”。实时页面越多，一屋子打开的标签页和 App 就越早达到该上限。

- 短信转发、其规则表单和转发日志不持有流（App 对它们都不做实时更新；转发结果作为主题延后实现）。
- 消息和会话只流式读取 `sms` 主题（推送、到达计数器；不采样）：流 URL 携带页面加载时的计数，后续到达时出现“新消息 · 刷新”（或“N 条新消息”）；列表本身不更新（按计划没有列表主题）。这些流的链接重新加载它们所在的页面（`href=""`），因为一条流服务于所有会话和过滤条件；在消息页上，显示“消息已发送”、“会话已删除”或删除失败后，该重新加载会再次显示提示行（已接受）。在会话中，提示位于回复栏正上方，气泡在从末尾开始的框中滚动（`column-reverse`），因此任何加载（包括重新加载）都会显示最新消息。每个打开的短信页面都像任何实时页面一样占用事件中心 8 条流中的一条。回复提交的回答（失败）没有流。
- 实时流量显示调制解调器自身的速率（`traffic`，App 的“实时蜂窝流量”）；App 的“估算”说明及其对其他计数器的回退在 Web 上不存在，因此没有这些速率时卡片显示“实时流量不可用”。
- 片段绝不包含表单、输入框或 `<details>`（SIM 服务的工具包片段 `#stk` 和 `#stk-nav` 通过 `form=` 持有属于片段外表单 `#stkf` 的提交按钮；添加 eSIM 的下载卡片 `#eadd-dl` 持有属于 `#eaddf` 的按钮：片段中没有 CSRF 或一次性令牌）：CPU 与温度上的“所有传感器”是包裹其片段的 `<details>`，始终在页面中（以便更新找到它），列表为空时由 CSS 隐藏（App 仅在有传感器时显示）；实时更新绝不会关闭它。Wi-Fi 与设备上的已连接设备是一个 `<details open>`（App 的卡片默认展开），其计数和列表作为片段放在其中。进程的“终止”按钮是指向确认页面的链接，因此实时列表不含表单。USB-C 卡片的文本和状态是其片段（`card-usb`，来自 `usb` 和 `charger`）；它的两个表单跟在片段之后，始终在仪表盘中，CSS 只在片段显示已插入线缆时显示卡片（且仅在快速充电关闭时显示“快速充电”），因此页面打开期间插入线缆会得到同样的按钮。
- USB-C 卡片的关闭是会话状态，因此没有片段读取它：仪表盘的页面加载及其流把它放进片段渲染所依据的视图，那里（或工具 › USB 模式页面加载时）读到已断开就会结束所有会话的关闭状态（下次插入时再次显示卡片，与 App 重新显示其面板一致）。只有打开的仪表盘会读取 `usb`：没有打开时拔下再插入线缆不会被察觉。插入线缆是否会触发固件的充电器事件（它会立即重读 `usb`）尚未在设备上验证；无论是否触发，10 s 一次的读取都能覆盖。
- 连接与信号上的 Web 新增：飞行模式下各面板为空白（固件保留其最后的读数），运营商卡片和图表会说明原因。图表的时间轴是相对的（“2 分钟前”到“现在”），而不是 App 的时钟时间。其折线在缺失读数或采样器暂停处断开：间隔超过 3 个采样周期，周期取相邻的较长间隔，保持在 2 s 到 10 s 之间（设置 › 轮询的节奏；混合节奏仍为一条线）。事件中心保留最后 120 个读数（`events::history`），因此 1 s 节奏可填满 2 分钟。
- 已知限制：桌面标签页在隐藏时若 Datastar 正等待重试断开的流，可能会在后台重新打开它；30 分钟存活期会结束它。
- **滚动数字**（所有者决策 57，App 的 `AnimatedNumber`：`.contentTransition(.numericText(value:))`，0.4 s ease-in-out；`web::roll`）。在实时页面上，当补丁改变一个数字时，其变化的数位会滚动：数值上升时向上（新数字从下方升起，旧数字向上离开），下降时向下；其他数位、符号、小数点和单位保持不动。位置（App 的动画值及其在 Web 上的位置）：

  | App（`AnimatedNumber` / `numericText`） | Web（片段：数字） |
  |---|---|
  | 仪表盘连接卡片的 RSRP | `card-conn`：NR/LTE RSRP |
  | 蜂窝卡片的实时速率和总量 | `card-traffic`（仪表盘和实时流量）：下载、上传、总下行、总上行 |
  | 电池卡片的 W / mA | `card-battery`：状态之后的功率 |
  | CPU 卡片的使用率、温度 | `card-health`：CPU %、CPU 和电池 °C；`hl-cpu`、`hl-temps`、`hl-all`（CPU 与温度，每个传感器）；`hc-use`、`hc-temp`（CPU 与内存） |
  | 电池详情的电压、电流、功率 | `bat-detail`：同样的三行 |
  | Wi-Fi 与设备数量、已连接设备数量 | `card-devices`（仪表盘）、`wf-count`（Wi-Fi 与设备） |
  | 信号监控指标（RSRP、RSRQ、SINR、RSSI）和整数行 | `sig-nr`、`sig-lte`（每个载波的网格；PCI、小区 ID、信道/EARFCN）、`sig-wcdma`（RSCP、Ec/Io） |

  | `LastUpdatedView`（“4 秒前”） | 导航栏的 `#age` 标记（仪表盘、连接与信号），始终像 App 的 `numericText()` 一样向上滚动 |
  | 设备控制的充电上限、恢复间隔 | 无对应 Web 实现：Web 的下拉框是表单，不是实时 |

  - 仅服务端，除 Datastar 外没有脚本。页面加载（因此所有没有 JavaScript 的页面）和流的首帧都按原样逐字节绘制纯文本：首次渲染或重连时不会滚动。每条流保留它绘制的数字（`Views::roll`）；文本变化的数字会为屏幕阅读器一次性绘制其完整文本（`.sr`），并另有一个 `aria-hidden` 副本（`.rl`），其中每个变化的数位是 `<i id="<key><place><digit>" data-u|data-d="<旧数位>">`。Datastar 的 morph 只在 id 匹配时保留元素，而 id 包含数位，因此变化的数位总是新元素，其 CSS 动画会运行，而未变化的数位是纯文本。在数字再次变化之前它都以同样方式绘制，因此未变化的数字不产生补丁，因其他原因重发的片段也不会重启任何东西。键按页面区分（`roll` 键为小写字母；有测试把每个实时屏幕渲染两次并检查数位 id 唯一）。
  - CSS：等宽数字（`.rl` 和所有承载滚动数字的元素）、列按行裁剪（`clip-path`）、旧数位作为 `::before`；`prefers-reduced-motion: reduce` 会关闭动画和离开的数位。方向与 App 一样比较数值（可识别 `1,024` 和前导负号；单位变化如 999.9 Kb/s 到 1.2 Mb/s 会向下滚动，与 App 一致）。
  - 开销：数字在再次变化之前一直保留其滚动标记（morph 正是借此保留 id），因此其片段的后续每次补丁都会为每条流上变化过的数字携带它：按流计的有界开销，没有额外帧。在假读取器测试夹具上实测（每个采样值每次采样都变化，比路由器更频繁）：仪表盘的流 1,605 到 2,343 B/s（+738 B/s），连接与信号 1,549 到 2,532 B/s，CPU 与温度 763 到 1,001 B/s；仪表盘每帧全部变化时，字节数 +32 %（2,280 到 3,012），渲染时间 +6 %（发布构建）。
  - 布局：`.rl` 为 `inline-block`；若规则给容器的每个 `span` 设置 `display` 会覆盖它并破坏行（连接与信号的网格曾经如此：应为 `.metrics .lbl` 而不是 `.metrics span`；`web::tests::no_rule_sets_display_on_every_span`）。

## 局域网 HTTPS

所有者决策 59（取代 56：不用 Tailscale）：Chrome 只从安全源安装 Web 应用（对 `http://192.168.0.1:9090/ui/login` 调用 `Page.getInstallabilityErrors` 只报告 `not-from-secure-origin`），因此 Agent 可以用**自己的证书颁发机构**在局域网上通过 HTTPS 提供 UI。离线、无账号；每台设备信任一次该 CA。:9090 上的明文 http 仍为 App 保留并作为回退。代码：`src/tls/`（管理器、`x509`、`hosts`）、`src/httpd/tls.rs`（监听器）、`src/web/pages/https.rs`（设置）。

**证书**（`tls::x509`，DER 手工构造并用 ring 签名，rustls 已链接它；根证书用 p256，实时活动也已链接它：不需要证书 crate，也不需要新增下载；`tls::x509::tests` 会解析回每个字段）：

| | 根（`ca.crt`） | 签发 CA（`issuing.crt`、`issuing.key`） | 服务器（`server.crt`、`server.key`） |
|---|---|---|---|
| 密钥 | P-256；签署签发 CA 后即**丢弃**（p256 的密钥在 drop 时擦除），绝不出现在磁盘上 | P-256，0600 | P-256，每次签发都新建，0600 |
| 主题 | `O=OpenU60 zte-agent, CN=U60 Pro local CA <8 hex>`（每个 CA 唯一） | `… CN=U60 Pro issuing CA <same hex>` | `CN=u60.home.arpa` |
| 有效期 | 从 2 天前起 10 年 | 相同 | 从 2 天前起 397 天，绝不晚于签发 CA |
| basicConstraints（critical） | CA，pathLen 1 | CA，pathLen 0 | 非 CA |
| keyUsage（critical） | keyCertSign、cRLSign | keyCertSign、cRLSign | digitalSignature |
| extKeyUsage | serverAuth | serverAuth | serverAuth |
| nameConstraints（critical） | permitted：IP `<LAN 地址>/32`（开启时为 `br-lan` 的 IPv4，若为私有）和 DNS `u60.home.arpa`；excluded：IP `::/0`，以及在未允许任何地址时还有 `0.0.0.0/0` | 相同 | — |
| SAN | — | — | DNS `u60.home.arpa`，CA 覆盖期间还有 LAN 地址 IP |

- **范围（所有者决策 59：“路由器的私有地址和一个本地名称”）。** CA 只能为服务器证书所需的内容背书：为其创建的 LAN 地址和 `u60.home.arpa`（及其下级名称）。因此，从路由器复制 `issuing.key` 的人只能冒充 `https://192.168.0.1` 和 `u60.home.arpa`（例如另一网络中同样位于 192.168.0.1 的路由器），而不能冒充所有私有地址和 `home.arpa` 名称。已测试：用保存的签发密钥为 `nas.home.arpa` + `192.168.5.5`、`192.168.0.2` 或 `10.20.30.40` 签发的证书会被 webpki（`tls::tests`）、OpenSSL 4.0.3 和 macOS 的信任评估拒绝（2026-10-24）。代价是：LAN 地址变更后，证书只包含 `u60.home.arpa`（hosts 行跟随新地址，因此该名称继续可用），设置会提示“重置 HTTPS 并重新开启”以覆盖新地址（每台设备随后信任新 CA）。开启时若 LAN 地址不在 10/8、172.16/12、192.168/16 内，则 CA 只覆盖名称（排除所有 IPv4 地址）。开启后修改的 `ZTE_AGENT_TLS_NAME` 也不会被覆盖；设置会说明这一点。
- **为何用两个 CA。** 解决这个问题的测试（2026-10-24，Android 16 模拟器，Chrome 133，根证书通过设置作为用户 CA 安装）：若只有一个受名称约束的根，则同时包含 `10.0.2.2` 和 `example.com` 的证书会无警告加载，`127.0.0.1` 的证书也一样：Android 的系统验证器（Chrome for Android 使用它）会忽略用户安装的信任锚的名称约束。链中有受约束的签发 CA 时，两者都被拒绝（“你的连接不是私密的”，凭据被打乱），而范围内的证书可以加载。每个验证器都会执行中间证书的约束（RFC 5280）；根证书的约束则保留给那些也遵守锚约束的验证器（Apple、OpenSSL 和 webpki 都会，已测试）。路由器上唯一的密钥（`issuing.key`）无法为约束之外的任何内容背书。真正起作用的是约束而非 `pathLen`：该密钥为自己签发的 CA（自签发，RFC 5280 不计入 `pathLen`；macOS 在安全审查中接受过一个）仍会继承约束，因此其为 `example.com` 签发的证书会被拒绝。排除 IPv6 是为了防止某个验证器把它当作独立的名称类型。两个 CA 上的 serverAuth 使它们无法用于代码签名和电子邮件（在 EKU 链式校验的地方：Windows、NSS、Chrome）。
- **397 天：** Apple 和 Chrome 将公开信任的 TLS 证书限制为 398 天；Apple 将所有 TLS 证书（包括用户信任的根）限制为 825 天，并要求 serverAuth 和 SAN。对于用户安装的根，CA 的 10 年不受该限制；到期后请重置。
- **时钟。** 快速启动开机后，路由器的时钟在网络通过 NITZ/NTP 设置之前是过期的，而固件的 NITZ 可能偏差 +8 h。因此：日期回退 2 天；`Tls::utc` 分为*已验证*（实时活动经 TLS 校验的 UTC，`LiveActivity::verified_utc`）、*未验证*（路由器时钟，不早于 2026-10-01 且不早于 CA 自身日期）或*未设置*。开启和续期是所有者动作，其问题会显示日期（并在未校验时说明）；它们会拒绝未设置的时钟。自动续期（剩余少于 30 天）需要已验证的时钟，且未经所有者绝不会使用路由器自身时钟（启动时也不使用）。**只有配置了实时活动 APNs 提供方时才有已验证时钟**（`ZTE_AGENT_LIVE_ACTIVITY_CONFIG`，需要 Apple 开发者密钥；见 README）：没有它，证书绝不会自行续期，大约每 13 个月设置会显示“证书即将过期”和最后 30 天的“续期证书”（`GET /api/https` 中的 `renew_due`）；到期后，设备会收到证书错误，直到通过 `http://192.168.0.1:9090/ui/settings` 的设置 › 续期证书。（在合理窗口内用未验证时钟无人值守地续期，是待定的所有者决策。）
- **重新签发，不用定时器：** 在 Agent 启动时（线程 `tls-start`，一次）、在 TLS 连接时（`Tls::wants_check`，仅在运行时线程的内存中：连接到达的私有地址既不是证书的地址、也不是上次读取的 LAN 地址，或按路由器时钟剩余不足 30 天；然后在阻塞池中 `check`，握手前最多等待 2 s，每分钟最多一次）以及 LAN 应用后（`router_lan_set`，提交的 `lan_ipaddr`，对 App 也一样）。当证书应具有的地址变化时（CA 覆盖新地址，或不覆盖：则只有名称），会用旧日期重新签发（不需要时钟）；hosts 行无论如何都跟随 LAN 地址，设置中的证书行每次都会重新计算（一切正常后清除）。新密钥会换入下一次握手（`tls::Keys`，由 rustls 解析器在每次握手时读取）；已打开的连接保留其密钥。
- **文件**位于 `/data/zte-agent-tls/`：目录 0700，密钥 0600（启动时若发现可被他人读取会再次设置），每个文件写到其名称旁、同步并重命名，然后同步目录。启动时缺失或损坏的服务器密钥对（保存新密钥与其证书之间断电、磁盘满）会用同一 CA 重新签发，旧证书仍可读取时按旧证书的日期（不需要时钟），否则用已验证时钟；两者都没有时保留 CA，设置会提示“开启 HTTPS 会用同一证书颁发机构签发新证书”（设备会继续信任它）。完全无法使用的文件会让 HTTPS 关闭并提示“开启 HTTPS 会新建证书颁发机构……；重置 HTTPS 会删除这些文件。”（此时关闭状态下会提供重置）。密钥绝不会被记录、渲染或提供（测试会检查 API 应答、描述文件和安装页面中是否有它们）。

**监听器**（`httpd::tls::supervise`，与 :9090 在同一个 current-thread 运行时）：它在 `Tls::subscribe` 上等待（一个 `watch` 通道，不轮询），HTTPS 开启时绑定 `0.0.0.0:9443`（`ZTE_AGENT_TLS_BIND`），重置时停止：端口关闭，其服务的所有连接结束（`watch` 发送端被丢弃；进行中的请求，如重置自身的应答，可能在 2 s 内完成；keep-alive 连接和实时流随后结束）。rustls 0.23 配 ring 提供方，TLS 1.3 和 1.2，ALPN `http/1.1`，64 个可恢复会话，每次启动都用新的 `ServerConfig`（重置也会丢弃所有可恢复会话，因此客户端无法恢复在旧 CA 下建立的会话），握手限时 10 s。链为服务器证书和签发 CA。同样的路由器、同样的移动侧检查（`mobile::Guard::twin`，自己的表和自己的 fail-open 标志，因此防火墙问题中的“本 Web UI 可能可访问”跟随任一监听器）、与 :9090 相同的连接上限并共享（`Caps`：共 64，每个 LAN 地址 16，回环保留最后 8）。绑定失败或监听器自行结束会在设置中显示（“已开启 · 未监听”、错误及**重试**，即开启），且只在此时重试：绝不循环。请求携带 `Secure` 扩展；Cookie 与源转换见[会话与 CSRF](#会话与-csrf)。握手在运行时线程上执行（路由器的 Cortex-A55 上每次约 1 ms CPU，按 M4 Max 上 94 µs 估算）；LAN 主机循环发起握手会受连接上限约束，并使 :9090 慢几毫秒，不会更多（没有限流：慢握手信号量会让一个停滞的客户端阻塞其他客户端）。

**本地名称**（`tls::hosts`）：`/tmp/hosts/zte-agent` 保存 `<LAN 地址> u60.home.arpa`（dnsmasq 的 `lan_dns` 实例在收到 SIGHUP 时重新读取 `addn-hosts` 目录 `/tmp/hosts`；`/tmp` 是 tmpfs，因此 Agent 每次启动都会重写该行）。只有变化时才写入，也只有变化时才发信号。文件先写为 `/tmp/.zte-agent-hosts.tmp`（放在目录旁，绝不放在目录内：dnsmasq 会读取那里的每个文件），以新建方式创建（`O_EXCL`，权限 0644：有人在该全局可写的 `/tmp` 中于该名称植入的链接会被删除，绝不跟随），然后重命名到位。SIGHUP 发送到 `/var/run/dnsmasq/dnsmasq.lan_dns.pid` 中的 pid（若其 `/proc/<pid>/comm` 为 `dnsmasq`），否则发送到 `/proc` 中的所有 `dnsmasq`，绝不发给其他任何东西（收到 SIGHUP 时 dnsmasq 还会为每个租约重新运行配置的 `dhcp-script`：需要在设备上确认）。重置会删除该行（并发送信号）。`ZTE_AGENT_TLS_NAME` 可设置 `.home.arpa` 下的另一个名称（其他值会被忽略并记录）。该名称仅在 HTTPS 上作为 Host（[请求处理流程](#请求处理流程)）。使用自有 DNS 的设备（Android 的私人 DNS 设为某个提供商、浏览器中的 DNS over HTTPS、VPN）可能看不到该名称；只要 CA 覆盖，地址 URL 始终可用。

**设置 › HTTPS 与安装为 App**（`pages::https`）：关闭时：“HTTPS 已关闭”和“开启 HTTPS”（以及当遗留了无法使用的文件或保留了 CA 时，显示原因和“重置 HTTPS”）；开启时：“HTTPS 已开启”（或“已开启 · 未监听”并带**重试**）、“证书有效期至 <日期>”（按路由器时钟剩余 30 天内显示“证书即将过期”和“续期证书”）、https 地址链接、“安装到你的设备”、“重置 HTTPS”（红色），以及页脚：HTTPS 上为“你正在使用 HTTPS……”，明文 http 上（不在 Tailscale 上，因为证书不包含其名称）为“此页面是明文 http。一旦此设备信任路由器的证书颁发机构（安装到你的设备），请打开 https://<地址>:9443/ui/ ……”；明文 http 上的登录页也这么说。开启的问题：会创建什么、每台设备需信任一次该机构、它只能为本路由器的 LAN 地址和名称背书（以及 LAN 地址变更后只有名称可用，直到重置）、路由器时钟（是否经互联网校验）、:9090 保持；若保留了 CA，会说明用它签发新证书。重置的问题：会删除什么、设备必须移除旧机构并信任新机构，以及在 HTTPS 上此页面将停止工作。安装到你的设备：根的名称、它能为哪些内容背书、其 SHA-256 指纹（只在字节对之间换行；屏幕阅读器一次读完整串）和 Windows 的 SHA-1“指纹”，各设备在哪里查看指纹（iPhone：安装前的“已下载描述文件 › 更多详情”；Mac：钥匙串访问；Android：受信任的凭据 › 用户；Windows：详细信息），以及大小写和分隔符不影响校验；在明文 http 上，说明页面和下载可能被网络中的某人一起篡改，以及如何对照无法被伪造的来源校验（在已信任该 CA 的设备上通过 HTTPS 打开此页面，或经 SSH 执行 `sha256sum /data/zte-agent-tls/ca.crt`）；两个下载、iPhone 和 iPad、Android、Mac、Windows 的步骤（Windows、macOS 和 Android 上的 Firefox 120+ 使用系统根；Linux 上手动导入），然后如何安装应用（Chrome：安装；iPhone 上的 Safari：••• › 共享 › 显示更多 › 添加到主屏幕；Mac 上的 Safari：添加到程序坞）以及 DNS 提示。描述文件：一个 `com.apple.security.root` 载荷，未签名（iOS 上显示“未签名”），其描述说明该 CA 能为哪些内容背书，id 来自 CA 的摘要（同一 CA 生成同一描述文件）。

- 清单（`/ui/manifest.webmanifest`）仍是一个不带 Cookie 获取的静态文件（没有 `crossorigin="use-credentials"`）：浏览器在安装时读取它，之后最多约每天刷新一次，因此按主题区分的清单无论如何都无法跟随切换，还会随之发送会话 Cookie，并可能让 Chrome 在每次切换时重建已安装应用；浏览器实时跟随的是页面的 `theme-color`。其 `theme_color` 为浅色页面的 `#f2f2f7`（Chrome for Android 在页面颜色过亮时的回退值）；其 `background_color` 保持图标的 `#0f172a`（启动画面在其上显示图标）。
- **Chrome for Android 的已安装应用可以保持登录打开**（所有者决策 61，标记跳转，`session::without_session`）。Chrome 将已安装 Web 应用的启动、主屏幕快捷方式或其他 App 的链接视为跨站，因此 `SameSite=Strict` 会话 Cookie 不会随之而来。登录还会设置 `zte_ui_signed_in=1`（`SameSite=Lax`、`HttpOnly`、与会话相同的 `Max-Age`、不含机密；退出登录以及发现会话不存在时清除）。从站点外部到达、带标记但没有会话 Cookie 的 GET 页面导航会得到一个小页面，它会带 `hop=1` 再次打开同一页面（meta refresh，带继续链接）：页面自行发起的导航是同站的，因此会话 Cookie 会随之而来，页面随后不带该标志 `303` 到自身。绝不连续两次（标志、同站请求或过期的会话 Cookie 表示会话已不存在：进入登录，并清除标记），只指向请求自身的 `/ui/` 页面（`next` 的字符集，无点段，绝不是实时流或资源），绝不用于 POST、fetch、框架或 API。在 Chrome 155 中用来自其他站点的链接检查：带标记时已登录，没有标记时进入登录页。

## 隐私

- 绝不渲染：IMEI（设备信息只显示其后 4 位，“…0042”；读取时只保留这些，因此完整号码绝不会到达渲染器；所有者决策，App 显示完整号码）、IMSI 和 MSISDN（路由器自身号码），SIM 卡页面的下述例外、完整 ICCID、完整 MAC 地址（`clients` 主题读取 MAC；只有渲染器会掩码）。仪表盘只显示连接了多少设备。设备信息不读取 SIM（App 会读取且不显示其中任何内容）。
- SIM 卡（所有者决策；App 显示完整值）：ICCID 和 MSISDN 显示为后 4 位（“…4242”），IMSI 显示为网络部分和后 4 位（“001/01 …4242”：卡片的 MCC 和 MNC 位于其前时使用，页面本来也会单独一行显示；否则用前 3 位和 2 位）。`sim` 主题携带完整值；只有这些渲染器能看到它们，流帧中也一样。PIN、PUK 和解锁码只在 POST 请求体中：绝不出现在 URL、页面、日志或令牌存储中（其摘要是带密钥的）；重新显示的面板字段为空。Agent 在命令行中把它们传给 `ubus`（调用期间可在 `/proc` 中看到），固件的 `zte_topsw_mdm` 有会把 PIN、PUK 和 NCK 打印到其日志的格式字符串（`mdm.str`；未在设备上确认）：两者都在 Web UI 之外。
- 添加 eSIM：激活码和确认码只在提交的请求体（multipart）和 Agent 的请求中：绝不绘制到页面（字段始终为空）、放入 URL、片段、结果行或日志，也绝不保留（没有草稿；令牌存储用进程密钥保存它们的 HMAC）。上传的照片只在读取和解码期间保存在内存中，随后丢弃；绝不存储或记录（解码进程通过管道获取它们，其 stderr 被丢弃，只写出其答案）。运营商的错误显示时不含任何形似激活码的单词。
- eSIM 配置文件：ICCID 显示为后 4 位（“…1234”）；配置文件在 URL 和表单中用不透明键命名（ICCID 与每进程密钥的 HMAC，16 个十六进制字符；完整 ICCID 只在进程内传给 Agent 的处理函数）；EID 做掩码（“•••• •••• •••• …1234”），除非页面被明确要求（`?eid=1`，显式 GET；绝不在片段、流帧、URL 或日志中）。配置文件名称、提供商和昵称按 App 的方式显示。上次列表读取的名称保存在内存中（按 ICCID），以便切换的实时卡片能命名其目标。
- SIM 服务：USSD 回答和工具包文本可能包含余额、号码或代金券代码：按原样显示（方案中的“无”：App 会显示它们，而掩码后的代金券无法使用），仅在已登录的 `no-store` 页面上，保存在发起请求的会话的内存中（10 分钟，退出登录时清除），绝不出现在 URL（`?u=` 是提交时使用的令牌）、日志或 `<title>` 中。为 SIM 输入的文本只会被提交（隐藏时在密码字段中）。携带 SIM PIN 或 PUK 的 USSD 代码会被拒绝，且绝不再次显示。
- 已连接设备显示 Wi-Fi 与设备所示内容（相同行的数据和掩码：名称、IPv4、MAC 后 2 个字节、无 IPv6）。其搜索提交到页面，与消息一致（因此其文本（可能是设备名）不出现在 URL、历史或 `next` 中；URL 中的 `q` 会被忽略），且只匹配显示的内容：掩码后的名称和 MAC 以及 IPv4 地址（搜索隐藏字节找不到任何东西）。读取失败为第一行（“无法更新：……”），与 App 的红色行一致；网络图标为次要灰色。
- Wi-Fi 与设备列出每个设备的名称（DHCP 主机名，否则主机提示名）和 IPv4 地址，MAC 掩码到最后 2 个字节（`••:••:••:••:3a:7f`；App 显示完整值），且不显示 IPv6 地址（所有者决策）。名称若拼出设备 MAC 的 3 个或更多字节（6+ 个十六进制数字，或用 `:` 或 `-` 连接的字节，如 `shellyplus1pm-02032ab12345`），这些字符也会被掩码。列表是实时的，因此这些也会出现在其流帧中；绝不出现在 URL 或片段 id 中。
- Wi-Fi 密码只出现在共享 Wi-Fi 页面：仅在“显示密码”（`?show=1`）之后以文本显示，以及页面始终显示的加入二维码中（与 App 的卡片一致）。页面从不实时，与所有页面一样为 `no-store`，密码绝不出现在 URL、日志或其他页面；显示的密码标记为 `translate="no"`。Wi-Fi 卡片的读取在渲染前丢弃密钥。已知限制：`no-store` 并不能可靠地让页面避开浏览器的前进/后退缓存（WebKit 可能保留它），因此在共享设备上，退出登录后按后退可能从内存中显示共享 Wi-Fi 页面；请关闭标签页。（`Clear-Site-Data` 也无济于事：浏览器只在安全上下文中遵守它，而 Agent 使用明文 HTTP。）
- 进程显示进程名和 PID（与 App 一致）。
- 短信页面显示与你通信的号码和消息正文，与 App 一样不做掩码（所有者决策），仅在已登录的短信页面上：绝不出现在 `<title>`（会话的标题是“会话”；号码是其标题）、URL 或查询字符串（会话用不透明键；搜索是提交到消息页的 POST，因此其文本只在页面中：随后存储项会把搜索表单提交到另一存储的页面，链接、流和 `next` 不携带搜索；输入到 URL 中的 `q` 会被忽略，登录时会丢弃它）、实时片段 id 或流帧、或日志中。渲染时间在所有地方都使用路由器自身的时区，按每条消息的日期（因此冬季消息在夏季仍保留其冬季时间；列表标签按路由器时钟计数，使用 App 的缩写词：“5 分钟前”、“1 个月前”、“2 分钟后”表示晚于它的时间；路由器时钟未设置时显示日期）。
- 转发机密（机器人令牌、webhook、Discord 和 Slack URL、头值、ntfy 令牌）绝不渲染：配置读取在任何渲染器之前丢弃它们，webhook 显示为其主机，规则表单的机密字段从不预填；输入到重新显示表单中的机密按其令牌保存在内存中，绝不在页面中，可能含有这类内容的被拒字段（ntfy URL 的密码或查询串、粘贴的 "Name: value" 头行）不会被回显。空的机密字段仅在相同目标类型和服务器下保留已保存的机密（新建规则/编辑规则下的合并规则），保存和测试都一样。聊天 ID、ntfy 主题和转发号码会显示，与 App 一致。转发器错误（测试、保存、日志、重试）会去掉 HTTP 客户端在其中两条消息中引用的 URI（"bad uri: <uri> …"、"configured for https only: <uri>"），该 URI 可能包含 webhook 路径或机器人令牌（`web::forward::redact`）。
- 转发日志显示每次转发的发送者和消息的前 80 字节（常为一次性验证码），与 App 一致，仅在已登录页面（任一标签页）；绝不显示消息全文或其日期，也不在 URL 中出现任何相关内容（重试表单提交 id 和时间）。
- WAN 地址、PCI 和小区 ID 只出现在已登录页面；小区锁定的 PCI 和 EARFCN、移动网络的运营商名称和 PLMN 也是如此（注册问题的 URL 携带 PLMN、RAT 和网络名称，不含个人数据）。
- “立即重启”、重启路由器和恢复出厂设置的路由器密码只通过 POST 发送，在路由器上以常量时间比较（计入登录限流，与登录使用相同的桶），且绝不回显、记录或保留。
- 偏好 Cookie（主题、刷新间隔）只保存固定值；不含任何关于会话、路由器或输入内容的信息。
- WiFi、访客 WiFi 和 APN 密码绝不绘制到页面、URL、片段或日志中（所有者决策；App 会填充它们）：读取在任何渲染器之前丢弃它们，字段始终为空（“留空以保留”），输入到表单中的密码在会话草稿中等待（内存，最后一次尝试后一小时，退出登录和发送后丢弃；失败的发送会保留它以便重试），绝不在页面中：问题页面的表单只携带令牌和草稿的随机修订号。令牌保存的摘要只覆盖修订号。
- 防火墙：MAC/IP/端口过滤的 MAC 地址只显示最后 2 个字节（`••:••:••:••:3a:7f`；App 显示完整值）；LAN 地址和端口按 App 的方式显示。
- DNS 缓存显示路由器设备查询过的域名（该网络的浏览历史），仅在已登录的 `no-store` 页面；其搜索使用 POST，绝不出现在 URL 或 `next` 中。
- AT 终端：回答是原始调制解调器输出，因此每段 14 位或更长的数字（IMEI、IMSI 或 ICCID；所有者决策：14–20）只显示最后 4 位（`•••••••••••0042`），存储的历史中也一样（完整号码绝不保留；在 4 KiB 截断之前掩码，因此截断绝不会留下明文的一部分）；“IMEI”快捷命令被省略。SIM PIN 和 PUK 绝不保留：从 `+CPIN=`、`+CPIN2=`、`+CLCK=` 或 `+CPWD=` 起，存储的命令和回答中每段 4 位或更长的数字都变为“••••”（调制解调器的回显）。较短的数字（`AT+CLCC` 或 `AT+CNUM` 中的电话号码）按调制解调器给出的显示。历史按会话保存在内存中，退出登录时清除；命令绝不出现在 URL 中（只有固定的快捷命令会）。“危险命令”问题以同样方式掩码命名该命令（其隐藏字段按原样保留，供“仍然发送”和取消使用）。
- 设备错误文本会转义并截断到 120 个字符。`?saved=` 提示来自固定表；`?r=<id>` 结果按会话查找，绝不从 URL 读取。
- 二维码的安全类型与 App 一致，只是没有 `encryption` 选项的网络（卡片称之为“开放”）编码为开放（`T:nopass`），而不是 WPA。
- Web 代码不记录任何日志。

- 局域网 HTTPS：`tls::x509::tests`（每个证书字段都解析回来；链用 rustls/webpki 对地址和名称验证，对约束之外的名称为和地址则拒绝，包括使用没有约束的根；路由器收窄后的范围和仅名称的 CA；范围可回读）、`tls::tests`（临时目录、假时钟、假 LAN 地址和假 dnsmasq：文件与权限、hosts 行与 SIGHUP、用已保存签发密钥伪造的证书被拒绝、启动、目录和密钥权限的修复、丢失或不匹配的服务器密钥对用同一 CA 重新签发（旧日期、已验证时钟，或保留给开启）、仅在已验证时钟上续期且绝不超过 CA、新的 LAN 地址（仅名称、相同日期、恢复后清除该行）、绑定失败后再次开启、重置、API 应答、描述文件）、`tls::hosts`（临时文件新建且在目录之外、植入的链接不被跟随）、`router::tests`（LAN 应用会移动 HTTPS）、`httpd::mobile`（每个监听器的 fail-open 标志）、`httpd::tls::tests`（监听器在 127.0.0.1 上，用只信任所生成根的 rustls 客户端：TLS 1.2 和 1.3、ALPN、链、本地名称仅经 HTTPS、按源的 Cookie 和源规则、热切换、握手前的延迟续期、重置与可恢复会话、重置结束实时流和 keep-alive 连接而其自身应答仍能通过、绑定失败与重试、监听器自行结束且不忙循环、握手前的移动侧检查、共享上限、经 TLS 的实时流）以及 `web::tests::https`（设置、问题及其一次性提交、保留的 CA、重试、安装页面、下载类型、提示、`GET /api/https`）。在路由器上：`openssl s_client -connect 192.168.0.1:9443 -servername u60.home.arpa -showcerts </dev/null` 会显示两张证书。
