# Agent OTA 更新

完成一次成功的 `setup.sh` 或 `deploy.sh` 引导后，U60 Pro 上的 Agent 无需 Mac 辅助即可自行更新。这些脚本会安装 A/B 槽位布局和小型启动监督程序。OTA 只重启 Agent，不会重启路由器，也不会主动中断 Wi-Fi 或蜂窝数据。

首次 Beta 硬件测试时，请引导已签名的预发布产物，而不是未签名的本地开发构建：

```sh
ZTE_AGENT_DOWNLOAD_URL=https://github.com/jesther-ai/open-u60-pro/releases/download/v2.4.0-beta.1/zte-agent ./setup.sh
```

## 安全模型

- 发布元数据由内嵌在发布构建中的离线 P-256 密钥签名；仅凭校验和不会被接受。
- 清单只能引用 `jesther-ai/open-u60-pro` 中不可变的发布资产，下载有严格的大小限制。
- 二进制会流式写入非活动槽位，校验其精确大小和 SHA-256 摘要，赋予可执行权限，并在提供安装前进行探测。连续 30 秒没有进展的读取会被中止，整次传输限时五分钟，残留文件会立即删除，并在启动时再次清理。
- 安装时会重复已签名的大小、摘要和兼容性校验，因此暂存二进制或其元数据损坏，不会产生待验证的启动试验。
- 测速、刚完成的 eSIM 切换、语音通话、USSD 会话、未充电且电量极低，或另一更新操作进行中时，安装会被阻止。
- 监督程序会观察候选版本 60 秒。若发生崩溃、本地监听不可用，或在提交前断电，则回到上一槽位。
- 启动时，监督程序会校验每个受管理槽位记录的大小、SHA-256 摘要和可执行探测结果。它会跳过被隔离的版本；当 A/B 两个选择都不安全时，可以启动单独保留的最后一个稳定版二进制。
- 全新的 SSH/USB 引导会写入两个槽位，并为每份副本记录摘要，因此在首次原生 OTA 更新之前就能发现意外损坏。
- 失败的版本会被隔离，避免自动检查反复暂存它。最后一次成功的稳定版构建也会单独保留。
- 所有修改类端点都需要已配置的 Agent 密码。自动检查默认开启；自动下载需主动启用；自动安装在当前版本中有意不支持。

下载端点运行在慢速工作通道中。运营商网络或发布服务器较慢时，不会占用更新状态、WebUI 和普通只读 API 调用所用的许可配额。

## 失败行为

| 场景 | 结果 |
| --- | --- |
| 通道数据缺失、格式错误或签名不正确 | 不下载任何二进制；运行中的 Agent 保持不变。 |
| 下载缓慢或停滞 | 30 秒空闲或总计五分钟的限制会中止下载；残留文件被删除。 |
| 负载被截断、过大或哈希错误 | 非活动槽位的下载在暂存前被拒绝。 |
| 下载后暂存二进制或元数据发生变化 | 安装预检失败，不会写入待启动标记或停止 Agent。 |
| 更新助手无法启动或无法确认交接 | 更新助手被停止，待启动标记被清除，当前 Agent 继续运行。 |
| 候选版本无法启动、监听或保持健康 | 候选版本被隔离，并重启已校验的上一槽位。 |
| 试用期间重启或断电 | 未通过验证的候选版本被排除，选择已校验的上一槽位。 |
| 之后某次启动时活动槽位损坏 | 监督程序选择另一个已校验且未被隔离的槽位。 |
| A/B 两个槽位都不安全 | 启动单独保留且已校验的最后稳定版副本，不将损坏的 A/B 槽位标记为活动。 |

有一个刻意保留的恢复边界：如果 A/B 两个二进制和最后稳定版救援副本全部缺失或损坏，设备上已没有任何可运行的更新程序。此时恢复需要 SSH/USB 和 `setup.sh`。验证时不得在生产路由器上故意破坏全部三份副本。

## 发布通道

- `main` 是生产分支。仅当 `vMAJOR.MINOR.PATCH` 稳定版标签指向当前 `main` 的精确头部时才会被接受。
- `beta` 是常驻的预发布分支。功能变更应先进入该分支；仅当 `vMAJOR.MINOR.PATCH-beta.N` 标签指向当前 `beta` 的精确头部时才会被接受。Beta 版本永远不会取代 GitHub 上的最新稳定版。
- 通过 `beta` → `main` 的拉取请求晋升已测试的版本。晋升合并并发布稳定版后，在下一个开发周期之前把 `main` 合回 `beta`，让两个通道共享生产修复。
- `v2.4.0-beta.1` 是最低更新器版本，这样第一个手动引导的 Beta 构建才能接收后续的 Beta 和稳定版发布。
- Beta 设备会同时考虑两个通道并选择较新的版本。切回稳定版时会丢弃任何 Beta 候选版本，并可从 Beta 构建回到当前稳定版构建。

发布工作流会把已签名的 `stable.json` 和 `beta.json` 指针写入 `ota-channels` 分支。设备在选择 OTA 时从不使用 GitHub 可变的 `latest` 重定向。

## 签名密钥设置

在可信的离线机器上生成一次密钥：

```sh
openssl ecparam -name prime256v1 -genkey -noout -out ota-private.pem
```

将完整的 PEM 保存为仓库的 Actions 密钥 `OTA_SIGNING_KEY_PEM`。私钥不得进入 Git、构建产物或路由器。对于带标签的发布，CI 只导出并内嵌公钥，构建静态 ARM64 二进制，对规范清单签名并更新相应通道。当密钥缺失、无效或不是 P-256 密钥时，发布标签按失败关闭处理。

## 扩大发布范围前的硬件验证

在物理 U60 Pro 上验证：首次 SSH 引导、启动持久化、`/data` 上的 A/B 符号链接更新、一次正常的手动更新、强制候选版本失败、试用期间断电、回滚、低电量延迟，以及 WAN、DNS 和 WebUI 持续可用。在该检查清单于目标固件上通过之前，自动安装应保持禁用。
